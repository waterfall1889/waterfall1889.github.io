# Application Architecture

## 1 SOAP

SOAP（**Simple Object Access Protocol**，简单对象访问协议）是一种用于**在网络上交换结构化信息的协议**，主要用于 **Web 服务**之间的通信。

### 1.1 SOAP 的工作流程

1. **客户端**构建一个 SOAP 请求（XML 格式）。
2. **客户端通过 HTTP 或其他协议**将请求发送到服务器端。
3. **服务器解析 SOAP 消息**，执行相应操作（如调用 Web 服务方法）。
4. **服务器生成 SOAP 响应**（XML），返回给客户端。
5. **客户端解析响应**，获取结果或错误信息。

### 1.2 SOAP 的优点

- **平台和语言无关**：任何能处理 XML 的系统都能通信。
- **支持复杂操作**：可用于远程过程调用（RPC），支持事务和安全扩展。
- **标准化**：SOAP 有 W3C 标准，企业级应用支持良好。

### 1.3 SOAP 的缺点

- **消息冗长**：XML 消息比较大，解析慢。
- **开发复杂**：相比 REST/JSON，SOAP 开发和调试更繁琐。
- **性能开销大**：适合企业级服务，但不适合轻量级 Web API。
- 和接口高度绑定，重构困难。

**WSDL**（Web Services Description Language，Web 服务描述语言）是一个**用来描述 SOAP Web 服务的标准化 XML 文件**。

## 2 Restful Service

REST（Representational State Transfer）是一种 Web 架构风格，强调**资源、状态和传输**。

### 2.1 Representational（表示）

- 所有数据都是 **资源（resource）**。
- 每个资源可以有 **不同的表示形式（representation）**，例如 JSON、XML、HTML。
- 每个资源都有 **唯一标识（URI）**。

### 2.2 State（状态）

- 指 **客户端的状态**。
- **服务器是无状态的（stateless）**，不保存客户端的状态。
- 资源的表示 **携带了客户端的状态信息**。

### 2.3 Transfer（传输）

- 客户端访问不同资源（不同 URI）时，会**传输客户端状态的表示**。
- 换句话说，**客户端状态通过资源表示在请求和响应中进行转移**。

### 2.4 主要操作

| 操作    | 含义         |
| ----- | ---------- |
| **C** | Create（创建） |
| **R** | Read（读取）   |
| **U** | Update（更新） |
| **D** | Delete（删除） |

| CRUD 操作 | HTTP 方法   | REST 语义                   |
| ------- | --------- | ------------------------- |
| Create  | POST      | 向服务器创建一个新的资源              |
| Read    | GET       | 获取资源的表示                   |
| Update  | PUT/PATCH | 修改已有资源（PUT 覆盖，PATCH 部分更新） |
| Delete  | DELETE    | 删除资源                      |

### 2.5 状态码

| 状态码类别         | 状态码 | 含义                    | 说明                    |
| ------------- | --- | --------------------- | --------------------- |
| **1xx 信息性**   | 100 | Continue              | 请求已接收，客户端应继续发送请求的剩余部分 |
|               | 101 | Switching Protocols   | 协议切换                  |
| **2xx 成功**    | 200 | OK                    | 请求成功，服务器返回请求的数据       |
|               | 201 | Created               | 请求成功并创建了新资源           |
|               | 202 | Accepted              | 请求已接受，但尚未处理完成         |
|               | 204 | No Content            | 请求成功，但没有返回内容          |
| **3xx 重定向**   | 301 | Moved Permanently     | 资源已永久移动到新 URI         |
|               | 302 | Found                 | 资源临时移动到新 URI（临时重定向）   |
|               | 304 | Not Modified          | 资源未修改，可使用缓存           |
| **4xx 客户端错误** | 400 | Bad Request           | 请求语法错误或参数错误           |
|               | 401 | Unauthorized          | 需要身份验证                |
|               | 403 | Forbidden             | 服务器拒绝请求，无权限访问         |
|               | 404 | Not Found             | 请求的资源不存在              |
|               | 405 | Method Not Allowed    | HTTP 方法不允许            |
| **5xx 服务器错误** | 500 | Internal Server Error | 服务器内部错误               |
|               | 501 | Not Implemented       | 服务器不支持请求的功能           |
|               | 502 | Bad Gateway           | 网关错误                  |
|               | 503 | Service Unavailable   | 服务器当前无法处理请求（维护或过载）    |
|               | 504 | Gateway Timeout       | 网关或代理服务器超时            |

### 2.6 无状态服务

**无状态是 REST 架构最核心的约束之一，其本质是服务器端不保存任何与特定客户端相关的会话上下文信息。**

- **请求自包含**：每一次客户端请求都必须携带服务端理解该请求所需的全部信息（如身份认证凭证、用户标识、分页参数、资源定位等）。
- **不依赖“上一次”请求**：服务器不会因为客户端之前访问过某接口，就默认本次请求拥有某种隐式权限或状态。任何请求都不能依赖服务端存储的历史交互数据。

#### 带来的核心优势

- **高可扩展性（Horizontal Scaling）**：任意服务节点完全对等。扩容时无需同步 Session，负载均衡可将请求随机分发到任何节点，无需“粘性会话（Sticky Session）”。
- **高容错性（Resilience）**：若某个服务节点宕机，用户的认证 Token 仍存在于请求头中，其他节点可无缝接管，用户会话不会丢失。
- **简化运维与开发**：无需搭建分布式缓存（如 Redis）来集中管理 Session，也无需处理 Session 过期、穿透等复杂问题，系统架构更清晰。
- **提升可见性**：监控或日志系统只需查看单一请求包，即可完整还原用户意图，无需关联上下文。

#### 代价与应对策略

- **额外传输开销**：每次请求都必须携带凭证（如 Token），增大了网络传输量。
  
  - *应对*：通常采用紧凑的 **JWT（JSON Web Token）** 或短小的 API Key 放在 `Authorization` 请求头中。

- **服务端计算压力**：服务端需每次都解析并校验 Token（如 JWT 验签），消耗 CPU 资源。
  
  - *应对*：利用 JWT 的本地自包含特性（不查库即可获知用户 ID 和权限），或引入网关层统一校验。

#### 与“缓存”的协同

无状态使得 **GET 请求的响应具有天然的可缓存性**。因为相同的 URI + 认证头组合请求任何节点，返回的表示完全一致，非常便于 CDN 或反向代理（如 Nginx）进行静态化缓存，显著提升性能。

## 3 单体应用与微服务

| 维度        | 单体服务  | 微服务     |
| --------- | ----- | ------- |
| **代码规模**  | 巨大    | 小而专     |
| **部署**    | 整体部署  | 独立部署    |
| **扩展性**   | 整体扩容  | 按服务扩容   |
| **技术栈**   | 单一    | 可多样     |
| **故障影响**  | 全局    | 局部      |
| **团队协作**  | 冲突多   | 边界清晰    |
| **运维复杂度** | 低（早期） | 高（需要体系） |
| **通信成本**  | 低     | 高       |

## 4 API Gateway

```text
客户端（Web / App / 第三方）
            │
            ▼
      API Gateway
            │
   ┌────────┼────────┐
   ▼        ▼        ▼
用户服务   订单服务   支付服务
   │        │
   └───▶  库存服务 ◀───┘
```

**API Gateway 是微服务系统对外的统一入口**，负责请求路由、认证鉴权和流量治理，屏蔽内部服务细节。

| 调用类型           | 是否经过 Gateway |
| -------------- | ------------ |
| 浏览器 / App / 前端 | ✅ 必须         |
| 第三方系统          | ✅ 必须         |
| 微服务 A → 微服务 B  | ❌ 一般不        |
| 定时任务 / MQ 消费   | ❌ 不需要        |

调用关系可以概括为：

- **客户端 → API Gateway**（对外统一 API）
- **API Gateway → 各微服务**
- **微服务 ↔ 微服务**（内部调用，不经 Gateway）

### 4.1 为什么微服务之间不走 Gateway？

若内部调用也走 Gateway，会产生严重问题：

1. **性能浪费**：每次内部调用多一跳网络，高并发下延迟放大。
2. **职责混乱**：Gateway 本应处理“南北向流量”，内部调用是“东西向流量”。
3. **单点瓶颈**：Gateway 成为内部通信总线，一旦出问题，服务之间全部瘫痪。

**正确做法**：微服务之间 **直接调用（HTTP / RPC / gRPC）**，或 **通过消息队列解耦**。

## 5 跨平台开发与故障处理

### 5.1 跨平台开发问题

- 移动端不同系统使用不同开发语言，容易产生大量重复业务逻辑，修改成本高。
- 一种思路是用 React / React Native 等框架实现多端互通。
- 设计上前端 UI 尽可能少掺业务逻辑，尽量交给后端完成。
- 另一种思路：每个服务自带数据库，服务间用消息队列通信，但通信成本较大。

### 5.2 微服务故障处理

危害性 ≈ 可能性 × 严重性。

- 故障后事后审计，评估风险。
- 设计时要考虑容错与服务等级（SLA）。
- **监控指标**发现故障，**链路分析**定位故障，**日志收集**分析错误。

## 6 服务注册与发现

服务启动后，把“我是谁、我在哪、我是否还活着”告诉一个统一的**注册中心**。

在单体或早期系统中：

- 服务地址往往**写死**（IP:Port）
- 机器数量固定，很少动态扩缩容

而在微服务中，服务实例随时会启动、宕机、扩容 / 缩容，IP 和端口**动态变化**。

若没有服务注册：

- 调用方不知道该连谁
- 配置文件会频繁修改
- 系统极不稳定

### 6.1 服务注册 / 发现流程

一个常见的**客户端服务发现**模式，典型闭环如下：

1. **服务注册（Service Registration）**：服务实例启动后向**服务发现 API / 注册中心**登记自身信息；注册中心侧常配合 **KV 存储**持久化元数据。
2. **定期拉取服务列表**：调用方内嵌的 Client 定期向注册中心请求可用实例列表，并缓存在本地。
3. **健康检查（Health Check）**：注册中心持续检测实例是否存活；异常实例被剔除，恢复后可重新注册。
4. **客户端负载均衡**：调用方根据本地缓存的实例列表，自行做负载均衡，再**直接**调用目标微服务（不经 Gateway）。

## 7 Eureka

- **Eureka** 是一个基于 REST 的服务注册与发现组件。
- **主要用途**：服务定位（service discovery）、负载均衡（load balancing）、故障转移（failover）。

### 7.1 核心组件

#### Eureka Server

- 提供服务注册与查询能力
- 是整个 Eureka 体系的中心服务

#### Eureka Client

- 基于 Java 的客户端组件
- 自动完成服务注册与发现，简化与 Eureka Server 的交互
- **内置负载均衡器**：使用 **轮询（round-robin）** 策略，属于基础级负载均衡

### 7.2 负载均衡层次

| 类型                   | 特点                                            |
| -------------------- | --------------------------------------------- |
| **Eureka Client 内置** | 简单轮询（Round-Robin），功能有限，适合基础场景                 |
| **Netflix 高级负载均衡器**  | 在 Eureka 之上封装，支持**加权负载均衡**，可参考流量、资源使用、错误状态等因素 |

## 8 配置中心（Configuration Center）

- **功能**：集中管理微服务的配置信息。
- **优势**：支持动态更新配置，无需重启服务。

## 9 微服务的通信方式

### 9.1 同步通信

- 使用 HTTP/REST 或 gRPC。
- **优点**：简单直接。
- **缺点**：服务之间耦合性较高，性能可能受影响。

### 9.2 异步通信

- 使用消息队列（如 Kafka、RabbitMQ）。
- **优点**：解耦服务，提高响应速度和容错性。
- **缺点**：增加系统复杂性。

## 10 微服务的优缺点

### 10.1 优点

- **独立性**：每个服务可以独立开发、部署和扩展。
- **技术多样性**：不同服务可以使用不同的技术栈。
- **容错性**：一个服务的故障不会影响其他服务。
- **可扩展性**：可以根据需求单独扩展某个服务。

### 10.2 缺点

- **复杂性**：系统架构和运维复杂度增加。
- **性能开销**：服务之间的通信增加了延迟。
- **数据一致性**：分布式事务管理复杂。
- **调试困难**：跨服务的调试和问题排查难度增加。

## 11 Serverless

Serverless 工作负载是“**事件驱动的工作负载**，不关心通常由服务器基础设施处理的方面”。

在 Serverless 环境中，开发者无需关心：

- 运行多少实例
- 使用什么操作系统
- 运行时环境（runtimes）
- 资源分配
- 扩缩容
- 安全及其他服务器层面的细节

以上问题均由平台自动管理。

### 11.1 FaaS（Function as a Service）

- Serverless 通常由 **FaaS 平台**实现。
- FaaS 负责：实例管理、扩缩容、运行环境、底层资源调度。
- 开发者只需编写函数逻辑。

### 11.2 典型特征

- **事件驱动（Event-driven）**：代码由事件触发执行
- 平台自动管理生命周期
- **可缩到零**
- **无状态（Stateless）**：函数本身不保存状态，状态需外部存储（数据库、缓存等）

## 12 微服务的实践建议

| 方面        | 建议                            |
| --------- | ----------------------------- |
| **服务拆分**  | 根据业务功能拆分服务，避免过度拆分             |
| **数据管理**  | 每个服务有自己的数据库，避免直接访问其他服务的数据库    |
| **通信方式**  | 优先使用异步通信，减少服务之间的耦合            |
| **容错与降级** | 使用熔断器（如 Hystrix）防止服务雪崩        |
| **自动化运维** | 使用 CI/CD 工具（如 Jenkins）实现自动化部署 |
