# MySQL Optimization

## 1 索引（Index）

优化 MySQL 等关系型数据库，需要理解底层存储思路。一个核心主题是**索引**。

索引本质上是一种用于**快速定位数据**的数据结构。它通常会额外占用存储空间，并增加 `INSERT` / `UPDATE` / `DELETE` 的维护成本；但合理设计索引可以显著降低查询扫描量，尤其适合等值查询、排序和范围查询。

在 MySQL 的 **InnoDB** 存储引擎中，索引主要基于 **B+Tree** 实现。

### 1.1 聚簇索引（Clustered Index）

聚簇索引是一种特殊索引：**数据表的物理组织顺序与索引顺序一致**，叶子节点**直接存储完整行数据**。

在 InnoDB 中，聚簇索引不仅是“查找结构”，也是数据本身的组织方式。

通常：

- 若定义了 `PRIMARY KEY`，主键索引即为聚簇索引
- 若无主键，InnoDB 会选一个合适的 `UNIQUE NOT NULL` 索引
- 若仍没有，InnoDB 会生成隐藏的聚簇索引

**一张表只能有一个聚簇索引**（数据只能有一种物理排序）。

对比：

| 类型 | 叶子节点内容 | 查找特点 |
| --- | --- | --- |
| **聚簇索引** | 完整行数据 | 找到索引即找到行，无需回表 |
| **非聚簇 / 二级索引** | 索引列值 + 主键（“指针”） | 常需再回表取完整行 |

#### 1.1.1 优缺点

**优点：**

- **查询快**：主键 / 范围查询可省去回表
- **物理有序**：利于 `ORDER BY`、`BETWEEN` 等范围访问

**缺点：**

- **插入代价**：非顺序插入（如 UUID）易引发页分裂
- **维护成本高**：改主键会导致整行物理移动
- **二级索引变大**：二级索引叶子存主键；主键过长会放大所有二级索引体积

### 1.2 为何常用 B+ 树

- 单节点可容纳较多键，与页存储契合
- 树高较低，查找快，结构调整相对不频繁

其他索引形态：

- 空间数据：R 树（空间索引）
- `MEMORY` 表：可支持哈希索引（等值很快）
- InnoDB `FULLTEXT`：倒排列表

### 1.3 索引不适用的情况

- **小表**：整表扫描往往已很快，索引额外跳转未必更快
- **几乎访问全部行**（如大报表）：按索引随机跳页代价高，顺序读整表可能更优
- **顺序读优于索引访问**：多数行都要读时，减少磁盘寻址往往更重要

## 2 主键设计

- InnoDB 默认在主键上建聚簇索引
- 主键不能为 `NULL`；若索引列可空，空值处理（如挂到链表）对性能很不利
- **多列主键**会使索引节点偏大、索引整体膨胀；更推荐**单独一列自增整数**做主键，业务唯一键可做二级唯一索引

## 3 表拆分（垂直拆分）

大表列很多、且查询常只涉及部分列时，整表扫描 / 宽行 I/O 成本高。

**做法：** 将不常用列拆到小表，用主表数字主键关联。

**好处：**

- 小表列少，单页可容纳更多行，提高缓存命中、减少 I/O
- 查询只 join 需要的列，避免拖带大量无用字段

## 4 索引前缀

对字符串列可用 `col_name(N)` **只索引前 N 个字符**，显著减小索引体积。

- `BLOB` / `TEXT` **必须**指定前缀长度才能建索引
- 前缀长度上限示例：
  
  - InnoDB：`REDUNDANT` / `COMPACT` 约 **767** 字节；`DYNAMIC` / `COMPRESSED` 约 **3072** 字节
  - MyISAM：约 **1000** 字节

查询时：若搜索值超过前缀长度，索引只能**排除明显不匹配行**，剩余行仍需回表精确比对。

## 5 复合索引（Composite Index）

可在多列上建一个索引（最多约 **16** 列）。列顺序很关键，遵循**最左前缀原则**。

### 5.1 最左前缀原则

对索引 `(col1, col2, col3)`：

| 可用 | 示例 |
| --- | --- |
| ✅ | `WHERE col1 = ?` |
| ✅ | `WHERE col1 = ? AND col2 = ?` |
| ✅ | `WHERE col1 = ? AND col2 = ? AND col3 = ?` |
| ❌ | 仅 `col2` / 仅 `col3`（跳过最左列） |

底层是按列顺序组织的 B+ 树：先按 `col1`，再在相同 `col1` 下按 `col2`……因此只有**从最左起的连续前缀**才能用于索引查找。

### 5.2 使用与设计要点

- 一个设计合理的复合索引，可覆盖多种“前缀列”查询，优于建多个单列索引
- 常用过滤列尽量靠前；若总是多列一起查，首列也可选区分度合适的列以利于压缩与选择性
- 尽量避免索引列大量 `NULL`

## 6 哈希索引

| 方面 | 说明 |
| --- | --- |
| **适用** | 等值比较（`=` / `<=>`），速度很快 |
| **不适用** | 范围查询（`<` `>` `BETWEEN`）、`ORDER BY`、估算范围行数、部分键前缀查找 |
| **场景** | 类似键值存储的单值查找；`MEMORY` 等场景可优先考虑哈希索引 |

## 7 降序索引（Descending Index）

- 索引定义中的 `DESC` 现已真正按**降序存储**键值
- 过去只能逆向扫描升序索引，效率较差；现在可正向扫描降序索引
- 复合索引中可混合升序 / 降序列，便于匹配 `ORDER BY col1 ASC, col2 DESC` 一类需求

## 8 表结构与行格式优化

### 8.1 列设计（Table Columns）

- 选用**尽量小且合适**的数据类型，节省磁盘与内存
- 能 `NOT NULL` 就声明：操作更快、索引利用更好、少判空开销（约每列省 1 bit）
- 仅真正需要时才允许 `NULL`

### 8.2 行格式（Row Format）

InnoDB 默认多为 **DYNAMIC**，也可通过 `innodb_default_row_format` 或 `ROW_FORMAT` 指定。

| 行格式 | 大字段行内 | 溢出 | 特点 |
| --- | --- | --- | --- |
| **REDUNDANT** | 前约 768 字节 | 剩余外部页 | 老格式，行内较浪费 |
| **COMPACT** | 前约 768 字节 | 剩余外部页 | 更省行内，去尾部空格 |
| **DYNAMIC** | 约 20 字节指针 | 内容多在外部页 | 行内最紧凑，适合大文本 |
| **COMPRESSED** | 约 20 字节指针 | 压缩存外部页 | 更省空间，CPU 开销更高 |

- `COMPACT` / `DYNAMIC` / `COMPRESSED`：对可变长字符列更省空间，但部分操作 CPU 更高
- 无可变长列时，固定长度行访问更快，但可能浪费空间；可用 `ROW_FORMAT=FIXED` 强制

### 8.3 索引相关建议

- **主键尽量短**：会出现在每个二级索引中
- **二级索引只建必要的**：过多会拖慢写
- **多列条件优先复合索引**，并认真设计列顺序
- **长字符串优先前缀索引**：更小、缓存更友好

### 8.4 Join 相关

- 很宽、常扫的表可垂直拆成“常访问小表 + 大字段表”
- Join 列**类型一致**，避免隐式转换
- 列名尽量简洁统一（如 `customer.name`），并注意跨库可移植性（列名不宜过长）

### 8.5 规范化与反规范化

- 默认遵循 **3NF**，用 ID 关联，避免重复存长文本
- BI / 大表分析场景可适度**冗余或汇总表**，用空间换查询速度

### 8.6 数值 / 字符串 / BLOB

**数值：**

- 能用数字列就不用字符串（更短、比较更快）

**字符串：**

- 不需要语言规则时，二进制 collation 更快
- 比较的列保持相同字符集与排序规则
- 较小字符串可用 `VARBINARY` / `VARCHAR`，减少临时表与排序开销
- 不常用长字符串可拆表；InnoDB 随机主键可考虑“时间等前缀 + 递增”改善插入局部性

**BLOB：**

- 可先压缩再存
- 大 BLOB 拆到独立表 / 设备，减轻主表内存压力
- 可对长文本存**哈希列并建索引**，查询先等值哈希再 `AND blob = 原值` 防碰撞

## 9 多表与规模限制

同一库表过多时：

- MyISAM 开 / 关 / 建表更慢
- 表缓存满时，多表查询会频繁换入换出

优化：增大表缓存。MySQL 对库 / 表数量本身限制很松，真正受限的是**文件系统**与**存储引擎**（如 InnoDB 表数量上限约 40 亿量级）。单表尺寸也受 OS / 文件系统约束。

## 10 行大小限制

InnoDB / MyISAM 最大行大小约 **65,535 字节**（统计方式因引擎与列类型而异）。

| 列类型 | 行内大致情况 | 行大小计入 |
| --- | --- | --- |
| `CHAR(10)` | 固定约 10 字节 | 计入完整长度 |
| `VARCHAR(1000)` | 前缀 + 长度信息等 | 前缀与指针等计入 |
| `TEXT` / `BLOB` | DYNAMIC 等多只存指针 | 通常计指针；内容在外部页 |

`BLOB` / `TEXT` 大内容多在外部页，主行主要受指针与短前缀约束。

## 11 存储引擎与 VARCHAR

实践中常见 **InnoDB** 与 **MyISAM**。InnoDB 大表可 `OPTIMIZE` 做碎片整理，并围绕主键组织聚簇索引；主键过长时宜另加自增列做主键。

优先 `VARCHAR` 而非过宽的 `CHAR`：

- `CHAR(N)` 固定占满，短值补空格浪费空间
- `VARCHAR(N)` 按实际长度 + 1~2 字节长度信息存储，短串更省
- 对 `NULL` 也更友好；变长行更紧凑，单页更多行 → 更好缓存命中

## 12 事务与刷盘

- 在默认自动提交下，一条 SQL 往往对应一次事务
- 过多小事务、每次提交都刷盘开销大；可调 `autocommit` / 批量提交，降低 fsync 频率
- 超大、长事务可评估降低隔离级别（常见 `READ COMMITTED` / `REPEATABLE READ`）换并发
- 特定场景可关闭部分检查（如唯一性检查）以提速，但需明确正确性代价

## 13 磁盘 I/O

**可能磁盘 I/O 过重的信号：** CPU 利用率不高（如 < 70%），但数据库很慢。可能原因包括 buffer 过小、页经 OS 缓存未直接落盘、`fsync` 过频等。

存储选型：

| 介质 | 更适合 |
| --- | --- |
| **SSD（非旋转）** | 随机 I/O：file-per-table / 通用表空间、undo、临时表空间 |
| **HDD（旋转）** | 顺序 I/O：系统表空间相关、doublewrite、binlog / redo log |

可调高 `innodb_io_capacity` 提高刷脏吞吐，避免 checkpoint 拖垮整体吞吐。

## 14 内存表优化

`MEMORY` 引擎场景下，等值访问优先考虑**哈希索引**（也可用 `USING BTREE` / `USING HASH` 显式指定）。

## 15 Buffer Pool

InnoDB 用 **buffer pool** 在内存中缓存数据页与索引页。

### 15.1 大小与实例

- 调整 `innodb_buffer_pool_size` 时按 **chunk** 增减，默认 chunk 约 **128MB**（`innodb_buffer_pool_chunk_size`）
- 总大小需满足：**chunk × 实例数 × 整数倍**
- 多实例可提高并发；实例彼此隔离，建议**每实例 ≥ 1GB**
- 实例数常见可配 **1~64**；脏页到一定比例时由各实例相关线程 flush

### 15.2 替换策略（LRU 变体）

- 新读入页**不直接放到最热端**，默认插入到 LRU 列表约 **尾部 3/8** 位置
- 页被真正访问后，再移到最近使用端（hot）
- 列表分 hot / old：未再访问的页留在偏旧段，优先淘汰
- 目的：避免一次性大扫描的冷数据长期霸占 buffer pool

## 16 预读（Read-Ahead）

InnoDB 可异步按 **extent** 预取多页进 buffer pool。

| 算法 | 思路 |
| --- | --- |
| **线性预读（Linear）** | 根据顺序访问模式，预测后续页 |
| **随机预读（Random）** | 根据缓冲池中已有页的分布预测，不依赖严格顺序 |
