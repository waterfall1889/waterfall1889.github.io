# Clustering

## 1 集群的定义和作用

集群把多台服务器组织成一个对外统一的服务入口。对用户来说，通常感知不到后面是多台机器，只是向同一个入口发请求。

主要作用：

- **可扩展性**：希望接近线性扩展（两倍机器接近两倍能力），实际往往达不到理想线性
- **可用性**：一台宕机时，其他节点仍可继续提供服务
- **透明接入**：客户端只面对统一入口，不必关心后端拓扑

## 2 代理

### 2.1 正向代理

- **定义**：多个用户通过同一个代理 IP 向外发送请求
- **例子**：VPN
- **特点**：客户端主动经由代理访问外部资源

### 2.2 反向代理

- **定义**：大量请求先打到一个统一入口 IP
- **功能**：常见用途是负载均衡
- **工作方式**：代理接收请求后，再调度、转发给不同后端服务器

### 2.3 集群和反向代理的关系

- 做集群时，对外形态本质上就是在做一个反向代理
- 大量请求进入统一入口 IP，再由该入口转发到不同服务器

### 2.4 集群的约束条件

- 集群内服务器之间需要满足一定同步/一致性约束，才能真正“拼”在一起
- 只有完成必要同步，容错才有基础

## 3 集群的属性与原则

### 3.1 冗余原则（核心原则）

集群背后的主要原则是**冗余（Redundancy）**：通过冗余获得更高可用性与容错能力。

### 3.2 RAS 属性

#### 3.2.1 可靠性（Reliability）

- **目标**：消除单点故障
- 部分组件故障时，系统仍能继续运行

#### 3.2.2 可用性（Availability）

- **目标**：提高总体可用性
- 常用近似：

$$
A = 1 - (1 - f\%)^{n}
$$

- $f\%$：单机故障率
- $n$：服务器数量
- $A$：整体可用性
- 增加节点数量，可提高整体可用性

#### 3.2.3 可维护性（Serviceability）

- 集群比单机更复杂
- 优势是支持**热升级（Hot Upgrade）**，尽量在不中断服务的情况下维护与升级

### 3.3 可扩展性（Scalability）

- **成本**：用标准硬件组集群，通常比依赖大型多处理器机器更便宜
- **在线扩展**：运行中可通过加机器扩容，通常比插 CPU 板卡中断更小

### 3.4 幂等性（Idempotency）

- **定义**：相同参数可重复调用，且多次调用与一次调用效果相同
- **HTTP**：GET 通常视为幂等；会基于当前状态改持久存储的方法通常不幂等（如部分 POST / PUT / DELETE 场景）

请求失败常见于三个时间点：

1. **请求已发出，方法尚未开始执行**：通常未改变服务器状态
2. **方法执行中但未完成**：可能留下部分副作用，需要回滚或补偿
3. **方法已完成，响应未成功返回客户端**：服务端状态已变，客户端不确定是否成功；这也是幂等性最关键的场景——重试不能再产生额外副作用

## 4 负载均衡逻辑和 Nginx

### 4.1 Nginx 的基本定位

- 基于 HTTP，核心能力之一是反向代理
- 与后台框架解耦，可代理任意支持 HTTP 的后端
- 常见能力：负载均衡、缓存、动静分离、多站点 / 虚拟主机代理

### 4.2 常见负载均衡策略

#### 轮询（Round-Robin，Nginx 默认）

- 按顺序把请求分给各应用服务器
- **优点**：实现简单、分配相对公平、无状态开销小
- **缺点**：不考虑实时负载；机器性能或请求耗时差异大时容易不均；默认无会话保持，有状态场景需另做 Session 方案

#### 最少连接（Least-Connected）

- 把下一个请求分给当前活动连接数最少的服务器
- **适用**：请求处理时间差异较大时
- **优点**：更跟实时负载，响应往往更均衡
- **缺点**：要跟踪连接数，有额外开销；连接数也不完全等于 CPU / 内存负载；默认同样无会话粘性

#### IP 哈希（IP-Hash）

- 按客户端 IP 哈希，决定落到哪台机器
- **优点**：同一 IP 可粘滞到同一服务器，利于本地 Session / 缓存
- **缺点**：大客户或 NAT 共享 IP 时易偏斜；增减节点会改变哈希分布；负载均衡效果通常最差，hash 不佳时可能长期打到少数机器；用户开关 VPN / 代理导致 IP 变化时，Session 可能丢

综合看，常见排序大致是：**最少连接 > 轮询 > IP 哈希**。  
另外还可按机器能力配置 **weight**，让资源不同的节点拿到相应比例的请求。

### 4.3 Nginx 的其他常见能力

- **缓存**：缓存静态或可缓存动态内容，降低后端压力
- **动静分离**：动态内容与 HTML / CSS / JS / 图片等静态资源分流
- **多站点代理**：按域名 / 虚拟主机把请求转到不同后端，共享 80 / 443

## 5 集群反向代理与 Session 过程

### 5.1 反向代理请求路径

1. 客户端向集群统一入口发 HTTP 请求
2. 反向代理（如 Nginx）接收并解析请求
3. 按负载均衡策略选择后端
4. 转发请求（可附加 `X-Forwarded-For` 等头）
5. 后端处理业务逻辑
6. 响应经反向代理返回客户端

### 5.2 无状态服务与 Session

服务尽量与本地状态解耦，调度会更灵活，可用性也更好。

常见状态外置思路：

- `localStorage` / Cookie / 隐藏域：可用，但都有安全边界问题
- **Redis 存 Session（推荐）**：服务器只持有 Session ID，真实会话数据放 Redis

| 维度 | Redis Session | Cookie / JWT |
| --- | --- | --- |
| 敏感数据存储 | 服务器侧 | 客户端 |
| 客户端可见性 | 通常不可见 | 可解码 |
| 篡改风险 | 相对难直接篡改 | 需签名校验 |
| 泄露后处理 | 可立即失效 | 往往难以及时撤销 |
| 权限即时变更 | 支持 | 通常不支持 |

注意：

- Redis 自身也要高可用；实例数常要求 $\ge 3$
- Redis 故障可能拖垮依赖它的会话体系
- 另一种做法是对用户 ID 哈希固定到某台机器，但难以保证负载均衡，也会牵涉幂等 / 故障迁移问题

### 5.3 Session 读写流程（Redis 方案）

1. 从 Cookie 取 Session ID；没有则新建
2. 后端用 Session ID 读写 Redis
3. 响应里回写 Cookie（Session ID）
4. 后续请求无论落到哪台后端，都从同一 Redis 读同一份会话

本地内存 Session 一般不推荐：下次请求若换机器就会丢状态；若用 IP 哈希硬粘滞，又会带回负载不均与宕机丢 Session 的问题。

### 5.4 关键点

- **服务器无状态 + 状态外置**：任意节点都可处理任意用户请求
- **集中存储保证一致性**：Session 更新写入共享存储后，各节点看到的是同一份数据
- **容错**：单台应用宕机时，请求可切到其他节点；Session 是否还在，取决于 Redis（或其集群）是否可用

## 6 数据库集群

### 6.1 组成要求

- 至少三个实例
- 需要 Admin API 一类工具，用一组命令完成配置
- 需要类似 Gateway 的 **MySQL Router** 负责转发请求

### 6.2 主从与读写分离

- **主（Master）**：负责写，也可承担部分读
- **从（Slave）**：主要负责读，并同步主库内容
- **写**：只能落到主库，再同步到其他节点
- **读**：在各节点间做负载均衡；主库因还要处理写，读请求可适当少分一些

### 6.3 MySQL Router

- 转发请求并做路由 / 负载均衡
- 写请求打到主库，读请求在节点间均衡分配
- 对应用相对透明，业务侧不必直接感知具体落到哪台库
