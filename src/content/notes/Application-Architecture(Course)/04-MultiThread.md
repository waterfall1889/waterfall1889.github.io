# Multi-Thread Management

## 1 进程与线程的内存模型

| 项目 | 进程 | 线程 |
| --- | --- | --- |
| **内存** | 拥有独立的地址空间，包括代码段、数据段、堆、栈等。 | 与同属一个进程的其他线程共享代码段、数据段、堆，但每个线程有独立的栈空间和寄存器。 |
| **系统资源** | 进程有自己的文件描述符、信号、环境变量等资源。 | 线程共享进程的大部分资源，包括文件描述符、全局变量等。 |

## 2 创建线程的两种方式

### 2.1 Provide a Runnable object

**原理：**

- `Runnable` 是一个函数式接口，只需要实现 `run()` 方法。
- `Thread` 构造函数接收一个 `Runnable` 对象，然后调用它的 `run()` 方法。
- `Thread` 类负责线程的创建和调度，`Runnable` 只负责业务逻辑。

**特点与优点：**

1. **避免单继承限制**：Java 只能单继承；若已继承其他类，实现 `Runnable` 仍可扩展功能。
2. **逻辑与线程分离**：业务逻辑写在 `Runnable` 中，线程控制写在 `Thread` 中，职责清晰。
3. **适合共享资源**：多个线程可以共享同一个 `Runnable` 实例，方便数据共享。

**缺点：**

- 语法略复杂，需要单独创建 `Thread` 对象。

### 2.2 Subclass Thread

**原理：**

- 继承 `Thread` 类，重写 `run()` 方法。
- 调用 `start()` 方法时，JVM 会启动新线程并执行 `run()` 方法。

**特点与优点：**

1. **语法简单**：无需额外 `Runnable` 对象，直接继承 `Thread`。
2. **方便扩展 Thread 的方法**：若需调用或重写 `Thread` 的特定行为，可以直接继承。

**缺点：**

1. **Java 单继承限制**：继承 `Thread` 后无法再继承其他类，灵活性差。
2. **线程逻辑与线程对象耦合**：逻辑代码和线程控制在同一个类中，不利于复用和共享。

## 3 线程睡眠与中断

### 3.1 sleep

`Thread.sleep(long millis)` 会让当前线程**进入阻塞状态**（Timed Waiting），指定时间内不参与 CPU 调度。

- **线程状态变化**：
  
  - 从 **RUNNABLE → TIMED_WAITING（阻塞）**
  - 等待时间结束后，线程回到 **RUNNABLE** 状态，等待 CPU 调度

- sleep 会释放 CPU 占用：线程进入阻塞状态后，不再占用 CPU 时间片。

- **注意**：sleep **不释放锁**。若线程在 `synchronized` 块中调用 sleep，它仍然持有对象锁。

### 3.2 中断

中断会带来异常抛出，需要进行处理（如捕获 `InterruptedException`）。

## 4 Join

`Thread.join()` 是 **Thread 类的方法**，用于**让当前线程等待另一个线程执行完毕后再继续执行**。

- 当前线程调用 `t.join()`，会**阻塞自己**，直到线程 `t` **执行完毕（终止）**。
- 相当于“我等你忙完再干自己的事”。
- 可以用于**线程间顺序控制**。

## 5 竞争与同步

线程竞争会带来饥饿、死锁等问题。解决数据不一致问题可以通过加锁实现。

### 5.1 synchronized

`synchronized` 用于**控制多个线程对共享资源的访问**，保证同一时刻**只有一个线程可以执行被保护的代码块或方法**。

- **互斥访问**：同一时刻只有一个线程可以进入 `synchronized` 修饰的方法或代码块。
- **可见性保证**：线程修改了共享变量，其他线程可以立即看到（由 Java 内存模型保证）。

同步机制围绕一个内部实体构建，该实体被称为**内在锁（intrinsic lock）**或**监视器锁（monitor lock）**。内在锁在同步的两个方面都起作用：

1. 保证对象状态的独占访问
2. 建立 **happens-before** 关系，从而确保可见性

### 5.2 Synchronized Statement（同步语句）

**Synchronized Statement** 是使用 `synchronized` 关键字修饰**一段代码块**的机制，用于在多线程环境下保护共享资源的访问，提供比同步方法**更细粒度**的控制。

### 5.3 可重入同步（Reentrant Synchronization）

一个线程不能获取另一个线程持有的锁，但**一个线程可以获取它自己已经持有的锁**。允许线程多次获取同一把锁，就形成了**可重入同步**。

典型场景：同步代码直接或间接调用了另一个也包含同步代码的方法，且两段代码使用同一把锁。

若没有可重入同步，线程在执行同步代码时就必须采取很多额外预防措施，以避免自己阻塞自己。

1. **可重入锁（Reentrant Lock）**：同一个线程可以重复获取同一把锁，而不会被自己阻塞。
2. **作用**：允许一个 `synchronized` 方法调用同一个对象的其他 `synchronized` 方法，保证逻辑安全且无需额外处理。

### 5.4 原子操作（Atomic Actions）

原子操作不能被线程交错执行，因此可以在**不担心线程干扰**的情况下使用。但这并不意味着**完全不需要对原子操作进行同步**，因为仍然可能发生**内存一致性错误**。

使用 **volatile 变量** 可以降低内存一致性错误的风险：对 volatile 变量的写操作会建立 happens-before 关系，确保随后对同一变量的读操作可以看到最新值。

## 6 Liveness（活性问题）

### 6.1 Deadlock（死锁）

- **定义**：两个或多个线程**永久阻塞**，互相等待对方释放资源，无法继续执行。
- **特征**：
  
  - 线程互相依赖对方的资源
  - 永远等待，不会自动恢复

### 6.2 Starvation（饥饿）

- **定义**：线程**无法获得共享资源**或长期无法执行，导致无法前进。
- **原因**：
  
  - 资源被“贪婪”的线程长期占用
  - 调度策略不公平
- **特征**：
  
  - 线程仍然存活，但长期得不到执行机会
  - 与死锁不同，线程不是被阻塞，而是“饿着”等不到资源

### 6.3 Livelock（活锁）

- **定义**：线程因响应其他线程的行为而不停地做“动作”，虽然线程没有被阻塞，但**无法做实质性进展**。
- **特征**：
  
  - 线程不断改变状态，但没有真正推进工作
  - 线程未被阻塞（不同于死锁）
  - 常发生在**线程相互响应的循环**中
- **比喻**：两个线程不停地互相让步、调整动作，却没有完成任务，就像两个人在门口互相躲避却不走进去。

## 7 Guarded Block

**Guarded Block（受保护的块）** 是一种**线程等待特定条件成立后再执行操作**的设计模式。

- **核心思想**：线程在执行某段代码前，先检查某个条件（guard condition）；若条件不满足，就**阻塞等待**，直到条件满足才继续执行。
- 常见于**生产者-消费者模式**或**资源池管理**。

自旋等待可以不用额外做上下文切换，但自旋判断会影响性能。更好的方法是在条件满足时调用 `notifyAll` 唤醒其他线程，不过依然存在竞争。

## 8 Immutable Object

**Immutable Object（不可变对象）** 是指**对象一旦创建，其状态（属性值）就不可改变**。

- 创建后，不能通过任何方法修改对象的内容
- 任何“修改”操作都会返回一个新的对象
- 若创建对象成本很低，可以考虑使用不可变对象以简化并发控制

## 9 更高级的并发控制方案

`java.util.concurrent` 提供了比基础同步更高级的控制能力：

| 方案 | 作用 |
| --- | --- |
| **Lock objects** | 支持更灵活的加锁惯用法，简化许多并发应用 |
| **Executors** | 定义启动与管理线程的高层 API，提供适合大规模应用的线程池管理 |
| **Concurrent collections** | 便于管理大规模数据集合，可显著减少显式同步需求 |
| **Atomic variables** | 最小化同步，帮助避免内存一致性错误 |
| **ThreadLocalRandom** | 在多线程环境下高效生成伪随机数 |

### 9.1 Lock 对象

- **定义**：比 `synchronized` 更灵活的锁机制，位于 `java.util.concurrent.locks` 包中。
- **主要类**：`ReentrantLock`、`ReadWriteLock`（及其实现 `ReentrantReadWriteLock`）
- **特点**：
  
  - 可尝试获取锁（`tryLock()`）而不会阻塞
  - 可中断获取锁（`lockInterruptibly()`）
  - 支持公平锁（first-come-first-served）
- **用途**：
  
  - 需要比 `synchronized` 更复杂的锁策略
  - 读多写少场景（使用读写锁提高并发度）

### 9.2 Executors（线程池管理）

- **定义**：高层 API，用于**创建、管理和调度线程**。
- **主要接口**：`Executor`、`ExecutorService`、`ScheduledExecutorService`
- **常用实现**：
  
  - `Executors.newFixedThreadPool(n)`：固定大小线程池
  - `Executors.newCachedThreadPool()`：动态线程池
  - `Executors.newSingleThreadExecutor()`：单线程顺序执行
- **特点**：
  
  - 避免频繁创建/销毁线程的开销
  - 易于管理大量并发任务

### 9.3 Concurrent Collections（并发集合）

- **定义**：线程安全的集合类，减少显式同步需求。
- **主要类**：
  
  - `ConcurrentHashMap`：高效线程安全的哈希表
  - `CopyOnWriteArrayList`、`CopyOnWriteArraySet`：写少读多场景
  - `BlockingQueue` 系列（如 `LinkedBlockingQueue`）：适合生产者-消费者模式
- **特点**：
  
  - 内部实现线程安全（如分段锁、原子操作）
  - 可以在高并发环境下安全操作集合

### 9.4 Atomic Variables（原子变量）

- **定义**：提供无锁线程安全操作的变量类型，位于 `java.util.concurrent.atomic` 包。
- **主要类**：`AtomicInteger`、`AtomicLong`、`AtomicReference`
- **特点**：
  
  - 使用 **CAS（Compare-And-Swap）** 实现原子操作
  - 避免了显式同步，减少内存一致性错误

### 9.5 ThreadLocalRandom

- **定义**：线程局部随机数生成器，位于 `java.util.concurrent` 包。
- **特点**：
  
  - 每个线程都有独立的随机数种子
  - 避免多线程使用同一个 `Random` 对象时的竞争问题
- **用途**：
  
  - 高性能生成随机数
  - 适合多线程环境，不需要同步

## 10 Virtual Thread

**虚拟线程（Virtual Threads）** 是 **Java 19+（Preview）引入的一种轻量级线程**，属于 **Project Loom** 的成果。

与传统线程（平台线程 / OS 线程）相比，虚拟线程：

- 不直接映射到操作系统线程
- 由 JVM 自己调度，而不是由操作系统调度

可以理解为**大量轻量级线程的抽象**，用于大规模并发而不会消耗大量操作系统资源。

| 特性 | 传统线程（Platform Thread） | 虚拟线程（Virtual Thread） |
| --- | --- | --- |
| **底层实现** | 对应操作系统线程 | JVM 管理调度（纤程） |
| **创建开销** | 较大（栈内存 + 内核资源） | 很小（轻量级对象） |
| **并发量** | 受限（几千或几万个线程就高开销） | 可以创建数百万线程 |
| **调度** | OS 调度 | JVM 调度，挂起/恢复快速 |
| **阻塞行为** | 阻塞线程占用内核线程 | 阻塞会挂起虚拟线程，不占用 OS 线程 |
