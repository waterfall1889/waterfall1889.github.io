# MongoDB

## 1 NoSQL 出现的原因

- **半结构化 / 非结构化数据**：传统关系型库处理这类数据较吃力
- **大数据与分布式存储**：关系库常用 B 树索引，随机 I/O 易成瓶颈；即便分区，也难彻底解决扩展问题
- **ACID 约束**：强事务语义会限制分布式与横向扩展

## 2 MongoDB 概览

MongoDB 是文档型数据库，数据以 JSON（BSON）文档存储。

### 2.1 主要特点

- **文档模型**：一个文档可含多个键值对，结构较灵活
- **高性能**：支持复杂索引（如 2D 地理空间索引），适合实时查询
- **高可用**：副本集（Replica Set）；主写从读，主故障时可切换
- **自动分片（Auto-Sharding）**：按分片键把数据分布到多机，便于水平扩展
- **灵活查询**：支持丰富查询与聚合（MapReduce、Pipeline 等）

### 2.2 适用与局限

**较适合：**

- 非结构化 / 结构多变的数据
- 高并发读写
- Schema 经常变化的业务

**局限：**

- 复杂事务能力弱于传统关系库
- 强一致、强事务场景通常不是首选

## 3 数据模型

### 3.1 文档 / 集合 / 数据库

| 概念 | 类比 | 说明 |
| --- | --- | --- |
| **文档（Document）** | 一行 | 最小存储单位，JSON/BSON；结构可动态变化 |
| **集合（Collection）** | 表 | Schema-Free，同一集合内文档字段可不一致 |
| **数据库（Database）** | 库 | 多个集合的容器；有独立权限；磁盘上常对应独立文件 |

建议：单个应用的数据尽量放在同一个数据库中。

### 3.2 主键 `_id`

- 每个文档都有唯一 `_id`，默认自动生成
- 用于唯一标识与快速定位

### 3.3 文档格式要点

示例：

```json
{"greeting": "Hello, world!", "foo": 3}
```

- 文档通常含多个键值对
- **键顺序有意义**：`{"a":1,"b":2}` 与 `{"b":2,"a":1}` 视为不同文档
- **同一文档内 key 不可重复**
- 同一集合允许不同结构的文档并存

### 3.4 集合命名

- 空字符串 `""` 不是合法集合名
- 不要创建以 `system` 开头的集合
- 用户集合名不应包含保留字符 `$`

### 3.5 子集合约定

可用 `.` 做命名空间组织，例如：

- `blog.posts`
- `blog.authors`

这只是命名约定；`blog` 与“子集合”之间没有强制父子关系，甚至不必真有名为 `blog` 的集合。

### 3.6 保留数据库名

| 库名 | 含义 |
| --- | --- |
| **admin** | 根库，常用于身份验证 |
| **local** | 不参与复制；可放仅属于本机的数据 |
| **config** | 分片场景下存分片元数据 |

## 4 索引

### 4.1 默认与复杂索引

- 每个集合默认在 `_id` 上建索引
- 支持更复杂的索引，例如 **2D 地理空间索引**，用于“附近点”等查询
- 索引加速读，但增加写维护成本；写多场景要权衡

### 4.2 Geo2D 与 MySQL 空间索引对比

**MongoDB Geo2D（网格）：**

1. 把平面划成网格单元
2. 把坐标映射进对应格子
3. 索引记录各格子中的文档位置
4. 查询先锁定相关格子，再做距离精筛（如 Haversine）

适合：附近用户 / 商家、半径范围查询、注册地等点查询。

**MySQL SPATIAL INDEX（R-tree）：**

1. 空间对象用最小边界矩形（MBR）概括
2. 内部节点存子树 MBR，叶子指向实际几何对象
3. 查询沿与范围相交的分支下降，再做精确空间关系判断

支持 `GEOMETRY` / `POINT` / `LINESTRING` / `POLYGON` 等，用 `SPATIAL INDEX` 创建。

| 特性 | MongoDB Geo2D | MySQL SPATIAL |
| --- | --- | --- |
| 数据结构 | 2D 网格 | R-tree |
| 维度 | 偏 2D 平面 | 2D / 3D 更常见 |
| 查询侧重 | 距离、范围点查 | 包含、相交等空间关系 |
| 几何复杂度 | 更适合点 | 更适合复杂几何 |

## 5 分片（Sharding）

把数据分布到多台服务器，实现水平扩展。数据可按分片键范围落到不同 Shard。

### 5.1 核心组件

- **Mongos**：路由；按分片键把请求转到对应分片
- **Config Servers**：存分片元数据（分片键、数据分布等）
- **Shard Servers**：实际存数据

### 5.2 何时考虑分片

一般先从非分片起步，需要时再切分片。常见触发点：

1. 单机磁盘不够
2. 写入超过单 `mongod` 能力
3. 希望更大比例数据常驻内存以提速

### 5.3 自动分片过程（概要）

1. 启用分片并选定分片键
2. **Chunking**：数据切成 chunk（默认常见约 64MB），每个 chunk 覆盖分片键连续范围，并分布到各 Shard
3. **自动均衡**：监控不均后迁移 chunk

### 5.4 查询路由与分片键

- **查询带分片键**：Mongos 可直达对应分片
- **不带分片键**：常需广播到多分片再合并结果

分片键类型：

- **范围分片**：范围查询更友好
- **哈希分片**：分布更均匀，减轻热点
