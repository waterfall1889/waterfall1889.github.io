# RAG：Retrieval-Augmented Generation

## 1 RAG是什么

RAG（Retrieval-Augmented Generation）是一种旨在解决大语言模型（LLM）“知其然不知其所以然”问题的技术范式。

它的核心是将模型内部学到的“**参数化知识**”（模型权重中固化的、模糊的“记忆”），与来自外部知识库的“**非参数化知识**”（精准、可随时更新的外部数据）相结合。其运作逻辑就是在 LLM 生成文本前，先通过检索机制从外部知识库中动态获取相关信息，并将这些“参考资料”融入生成过程，从而提升输出的准确性和时效性。

### 1.1 RAG、MCP连接数据库和fine-tuning的区别

- RAG（检索增强生成）不会改变模型本身，他从外部知识库或者向量数据库检索文件，把文档和问题给模型，“阅读理解”回答。这个过程中，可能涉及到优化query、补全query等等过程。这个过程只需要保证数据库或者知识库及时更新即可，可以有效避免幻觉问题。而且适配各种非结构化的数据类型。

- Fine-tuning会用数据参与训练模型，把新的知识写入模型参数，需要重新采集数据、训练、部署模型，周期长。可能产生“一本正经地胡说八道”的幻觉，知识固化在参数中，不易修正。但是推理延迟低。

- MCP连接数据库：模型通过标准协议（MCP）主动调用外部工具/数据库，实时获取数据后组织回答。适合结构化实时数据，若查询逻辑正确，返回的是精确事实数据，幻觉极低。不过，推理延迟较高，要求模型具备**工具调用/函数调用**能力。

### 1.2 幻觉问题

- 在 AI 大模型领域，**幻觉** 指的是模型生成的内容看似通顺合理，但实际上**毫无事实依据、与真实世界不符，或完全捏造**的现象。

- RAG 给模型提供了一个“标准答案参考区”，限制了它自由发挥的空间。**原理是把“开卷考试”的参考资料直接塞给模型。**  模型不再需要仅凭自己“记忆”（参数）来回答，而是先检索出最相关的文档片段，然后被要求“**请严格根据以下资料回答问题**”。且这种策略保证了回答是可溯源的。

- RAG依旧可能带来幻觉，原因很多：
  
  - **检索环节出错**：检索系统没找到真正相关的文档，而是给了一堆无关的段落。模型很“老实”，基于这些无关资料强行生成答案，就会答非所问或编造连接。
  
  - **模型误解资料**：小型模型阅读理解能力有限，造成无法有效结合文档上下文理解含义，或者误解含义
  
  - **模型忽视资料，坚持“记忆”**：若模型在预训练时对某个知识印象很深（即使是错的），它可能无视你给的RAG资料，去输出自己“记忆”里的错误答案。这是“记忆”与“资料”的冲突。
  
  - **过度推理和融合**：模型可能把资料A和资料B的信息，通过错误逻辑组合出一个资料里根本没有的新结论，从而产生新的幻觉。
  
  - **资料本身有错**：如果文档库里有老旧或错误版本，RAG 会把错误当真原样输出。

## 1.3 知识图谱和RAG的对比

| 维度             | 知识图谱 (KG)                                                           | RAG (检索增强生成)                                           |
| -------------- | ------------------------------------------------------------------- | ------------------------------------------------------ |
| **知识表示形式**     | **结构化**：实体、关系、属性构成的三元组 `(头实体, 关系, 尾实体)`，以及逻辑规则。                     | **非结构化/半结构化**：通常将文档切分为文本块（chunk），以向量形式存储。              |
| **存储方式**       | 图数据库（如 Neo4j、NebulaGraph）或三元组库。                                     | 向量数据库（如 Milvus、Pinecone、FAISS） + 原始文本存储。               |
| **检索机制**       | **图遍历 / 路径查找**：基于实体链接、关系匹配、子图查询（如通过 SPARQL、Cypher 语言）。              | **向量相似度搜索**：将查询编码为向量，计算与文本块向量的余弦距离（或其他相似度），必要时混合关键词检索。 |
| **语义理解深度**     | 显式关系推理：能进行多跳推理（例如“A 的父亲的母亲” = A 的祖母），依赖预定义的本体模式。                    | 隐式语义匹配：通过稠密向量捕获自然语言中的上下文相似性，但不显式建模实体间的关系类型。            |
| **推理能力**       | **符号推理**：支持逻辑推理（传递性、对称性、一致性检查），可以回答需要多条关系路径的问题（如“X 和 Y 是否存在间接关联？”）。 | **概率匹配**：基于统计相似度，无法执行严格逻辑推理，但适合处理模糊、开放域的问题。            |
| **数据构建成本**     | 高：需要本体设计、实体对齐、关系抽取、消歧等，通常依赖人工标注或复杂的信息抽取 pipeline。                   | 相对低：只需文档切分、清洗、嵌入向量（可自动完成）。                             |
| **查询类型优势**     | 适合**精确的、多跳的、带约束的**问题（例如“请列出所有出生于巴黎、获得过诺贝尔物理学奖的科学家”）。                | 适合**模糊的、描述性的、需要总结或生成**的问题（例如“请用一段话总结本文关于气候变化的观点”）。     |
| **与 LLM 交互方式** | 将检索到的子图序列化为文本（如 JSON 或自然语言列表）嵌入 prompt；或使用图神经网络将图特征注入模型。            | 将检索到的相关文本块直接拼接在 prompt 中，由 LLM 生成答案。                   |
| **典型局限**       | 知识覆盖稀疏（易出现实体缺失）；对开放式自然语言问题的泛化能力弱；无法处理非事实性知识（如观点、情感）。                | 对需要多步逻辑推理的问题表现较差（例如“A 的竞争对手的供应商是谁”）；容易受切分粒度影响。         |

## 2 RAG的基本原理

## 2.1 RAG的主要解决的问题

- 知识的局限性：信息滞后，而训练一次的成本非常巨大

- 幻觉问题：参考1.2的内容

- token大小问题：目前的模型token大小已经增大很多，但是基于非常长的文档进行直接问答很困难，且这些长prompt的token会带来很高的成本，并且时间上会很长

### 2.2 RAG三个阶段

RAG发展经过了**原始RAG（naive RAG）、高级RAG（Advanced RAG）、模块化RAG（Modular RAG）** 三个阶段。

不过，整体来说，RAG可以分为两个大的部分，在线和离线部分。

- **离线部分**：对于知识库文档进行解析拆分、索引构建和入库，做chunking分段处理，用Embedding model进行转化成向量，存入向量数据库，同时基于元数据给出索引构建

- **在线部分**：query接受和分析，可以把Query进行优化和转换为Embedding vector进行向量数据库的近似匹配，然后也可以进行Rerank精细重排序，找到最后确定的数据块，把这部分和Prompt一起提供给LLM。最终生成更可靠的答案。

#### 2.2.1 原始RAG/基础RAG

- 只具备最基础的部分，“检索+生成”两步走。

- 主要包括三个组成部分：**离线索引构造、在线检索和大模型生成**

- 细节：Retrieve-Read框架
  
  - 索引（Indexing）：索引首先清理和提取各种格式的原始数据，如 PDF、 HTML、 Word 和 Markdown，然后将其转换为统一的纯文本格式。为了适应语言模型的上下文限制，文本被分割成更小的、可消化的块（**chunk**）。然后使用嵌入模型将块编码成向量表示，并存储在向量数据库中。这一步对于在随后的检索阶段实现高效的相似性搜索至关重要。知识库分割成 chunks，并将 chunks 向量化至向量库中。
  
  - 检索（Retrieval）：在收到用户查询（Query，**在Naive RAG中，通常不会对用户Query做出优化，直接使用用户的输入请求**）后，RAG 系统采用与索引阶段相同的编码模型将查询转换为向量表示，然后计算索引语料库中查询向量与块向量的相似性得分。该系统优先级和检索最高 k （Top-K）块，显示最大的相似性查询。这些块随后被用作 prompt 中的扩展上下文。Query 向量化，匹配向量空间中相近的 chunks。
  
  - 生成（Generation）：提出的查询（Query）和选定的文档（Chunks）被合成为一个连贯的提示，大语言模型负责生成回复。该模型的答复方法可能因具体任务的标准而异，允许它或者利用其固有的参数知识，或者限制其对所提供文件中所包含的信息的答复。在正在进行的对话中，任何现有的对话历史都可以整合到提示中，使模型能够有效地进行多轮对话交互。

- 特点：
  
  - 结构简单、实现容易
  
  - 无复杂后处理或优化
  
  - 检索质量直接影响最终结果
  
  - 通常使用“相似度最高”作为唯一检索标准

- 缺点：
  
  1. `检索精度不足`：仅依赖向量相似度做 Top-K 召回，准确率和召回率容易难以兼顾，常出现召回块与问题相关度不高、或关键信息未被召回的情况。对此，仅仅依赖HNSW等进行向量相似度的评估是不够的，需要考虑重排优化。
  
  2. `Query 未优化`：直接使用用户原始输入检索，对口语化、歧义、缩写或多意图问题缺乏改写与扩展，查询与文档在语义空间中的对齐往往较差。
  
  3. `分块质量粗糙`：多采用固定长度切分，容易在句段中间截断，破坏语义完整性，导致检索到的片段上下文不完整。
  
  4. `无重排序与过滤`：检索结果不经 Rerank 或元数据过滤即送入 LLM，噪声块、重复块和过时内容会一并进入上下文。
  
  5. `复杂问题处理能力弱`：单次检索难以支撑多跳推理、对比归纳或跨文档综合类问题，面对长文档、多实体关联时容易信息不足。
  
  6. `生成阶段仍易幻觉`：即使提供了检索上下文，模型仍可能误解资料、忽视资料或过度融合，产生与证据不符的回答。
  
  7. `上下文利用效率低`：将多个检索块简单拼接进 Prompt，冗余信息会挤占有效 token，既增加成本，也干扰模型对关键信息的识别。

#### 2.2.2 高级RAG

为了解决索引问题，Advanced RAG 通过多种优化方法优化RAG过程。主要是**检索前和检索后策略（pre-retrieval and post-retrieval strategies）**。

高级RAG（Advanced RAG）是围绕常规的“索引构建-检索-生成”流水线做了大量的优化、流程控制和自省机制的增强系统。比如文本分块的优化、重排策略、元数据优化、混合搜索、Query优化等等策略。

#### 2.2.3 模块化RAG

- 传统的朴素、传统RAG存在很多问题，核心的问题是对查询的理解不深入，难以涉及查询和文档之间的关系深度探究
- 检索存在冗余和噪声。 将所有检索到的块直接输入到 LLMs 并非总是有益。研究表明，过多的冗余和噪声信息可能会干扰 LLM 对关键信息的识别，从而增加生成错误和幻觉响应的风险。
- 因此，提出了大量优化RAG的方法和高级RAG，尽管高级RAG有所改进，但是仍然与实际应用与需求之间存在差距：随着 RAG 技术的发展，用户期望提高，需求持续演变，应用设置也变得更为复杂。例如，异构数据的整合以及对系统透明度、控制和可维护性的新需求。
- 为达成更精准和高效的任务执行，现代 RAG 系统正逐步融合更复杂的功能，比如以**知识图谱**的形式构建更精细的索引库，通过查询构建方法整合结构化数据 ，以及运用微调技术让编码器更好地适应特定领域的文档 。

<img title="" src="https://picx.zhimg.com/70/v2-77ecdf8a83ca847aed4310e21c1977e3_1440w.image?source=172ae18b&biz_tag=Post" alt="【RAG技术论文】《模块化RAG（Modular RAG）: 将RAG系统转变为乐高玩具一样的可重构框架》" width="814">

- 2024年7月的论文《模块化RAG（Modular RAG）: 将RAG系统转变为乐高玩具一样的可重构框架》提出了模块化RAG的概念:[[2407.21059] Modular RAG: Transforming RAG Systems into LEGO-like Reconfigurable Frameworks](https://arxiv.org/abs/2407.21059)

- 当前RAG系统已经超越了传统的线性检索-生成范式。研究人员采用**迭代检索**、**递归检索**以及**自适应检索**，使系统更具灵活性与自主性。这种灵活性大大增强了RAG系统的表达能力和适应性，使其能够应对更多样化的应用场景。
  
  然而，这也带来了工作流程编排和调度的复杂性，给系统设计提出了新的挑战。
  
  1. **复杂数据源的集成**。RAG系统不仅处理非结构化文本，还集成了半结构化数据（如表格）和结构化数据（如知识图谱）。访问这些异构数据源为系统提供了更加丰富的知识背景和更可靠的知识验证能力。
  2. **系统可解释性、可控性和可维护性的新增需求**。随着系统复杂度的增加，维护和调试变得更加困难。当问题发生时，快速定位并优化特定组件显得尤为重要。
  3. **组件选择与优化**。RAG系统中的神经网络越来越多，需根据任务和资源选择合适的组件。同时，额外组件虽增强了系统能力，但也带来了新的协同工作要求。确保各模型有效协作、提升整体性能成为关键。
  4. **工作流程编排和调度**。各组件可能需按照特定顺序执行，或在特定条件下并行处理，甚至由LLMs根据不同输出进行判断。合理规划工作流程对于提升系统效率和实现预期效果至关重要

- 模块化RAG系统由多个独立模块组成，这些模块通过紧密协调共同完成任务。该架构分为三层：
  
  - **顶层**关注RAG的关键阶段，将每个阶段视为独立模块，继承了高级RAG的主要流程并引入了编排模块来协调流程。
  - **中间层**包括各模块内部的子模块，进一步优化功能。
  - **底层**由基本的操作单元组成。
  
  在模块化RAG框架下，RAG系统可通过计算图形式表示，节点对应特定的操作符。模块化RAG基于先前RAG技术的发展演变而来。高级RAG可看作模块化RAG的一个特例，而基础RAG则是高级RAG的特例。

- 六个模块：
  
  - **A.Indexing**: 索引的核心是把文档分为可管理的内容块，并进行存储和索引构建。现在的主要问题是，常规索引会造成**内容表达不完整（分割方式会影响块的语义信息，导致重要信息在较长的上下文中被丢失或忽略）、块相似度搜索不准确（随着数据量增加，检索中的噪音变多，导致错误数据的匹配频率增加，使得系统不够可靠）、引用链模糊（检索到的块可能来自不同文档，尽管内容在语义上相似，但实际可能涉及不同主题）** 等等问题。因此与多种思路对于索引构建进行优化。
  
  - **B.Pre-Retrieval**：基础RAG的一大问题是过于依赖用户的原始查询，导致检索效果不佳。具体问题包括：查询措辞不当和语言中的歧义性，这可能导致错误检索结果。因此需要通过很多方式优化Query。
  
  - **C.Retrieval**：在RAG系统中，检索过程至关重要。通过向量模型，可以将查询和文本高效转换为潜在空间中的向量，帮助建立问题与文档之间的语义相似性，从而提升检索效果。检索需要关注三个关键点：**检索效率、质量**以及**任务、数据与模型的一致性**。
  
  - **D.Post-Retrieval**：将所有检索到的内容直接输入LLM并不是最佳做法。对这些块进行后处理有助于更好地利用上下文信息。主要挑战包括：
    
    - 1）**中间遗忘效应**。与人类一样，LLM倾向于记住长文本的开头和结尾，而忘记中间部分。
    
    - 2）**噪声与反事实块**。噪声或内容矛盾的文档会影响生成质量。
    
    - 3）**上下文窗口限制**。即使检索到大量相关内容，LLM的上下文长度限制使其无法处理所有内容。
    
    因此需要做重排/压缩/选择/评估
  
  - **E.Generation**：利用LLM，根据用户的查询和检索到的上下文信息生成答案。应根据任务需求选择合适的模型，并考虑微调需求、推理效率和隐私保护等因素。
  
  - **F.Orchestration**：**编排**控制RAG流程的模块。与传统的固定流程不同，RAG现在能够在关键时刻进行决策，**并根据前一结果动态选择后续步骤**。模块化RAG具备这种自适应和模块化的能力，区别于基础Naive和高级RAG范式。

## 3 具体RAG优化策略

### 3.1 文本分块优化策略（Indexing阶段进行）

文本分块是将需要检索的长文档切分成更小的片段（即“块”），以便于索引和检索。RAG 管道处理的是这些文本块，而非整个文档，因此文本块的质量直接影响检索准确性和答案清晰度。如果文本块过长，AI 模型可能会被干扰；如果过短，则可能丢失上下文。找到合适的平衡点有助于获得最佳结果。

块的大小和重叠程度直接影响RAG系统的性能。较大的块能提供更多上下文信息，但也会引入更多噪声，增加处理时间和成本。较小的块则噪声较少，但可能无法完整传达上下文。为了提升效果，使用带有重叠的滑动窗口可以改善语义过渡，但也有控制上下文尺寸困难和语义失准的缺点。

- **简单分块：** 将文档分割成固定大小且略有重叠的块（例如，35 个字符，重叠 5 个字符）。这种方法易于实现，但不考虑语义结构，可能将关键思想分割到不同块中。

- **语义分块：** 利用嵌入和余弦阈值，根据相似性对句子进行分组。这种方法能保持相关思想的完整性，提高检索精度，但需要像 BERT 这样的嵌入模型以及更高的计算性能。

- **基于语言模型的分块：** 使用大型语言模型（LLM）将文本分割成独立的语义单元。这种方法能产生高度连贯的结果，但计算成本高昂，可能需要进行微调。

### 3.2 重新排序策略（Post-Retrieval阶段进行）

在 RAG 系统中，初始检索器会获取大量的检索信息，其中有好的，也有不理想的。重新排序（Reranking）是指在将结果传递给大型语言模型（LLM）之前，对检索到的结果进行重新排列，使最相关的信息排在前面。

原有的顺序可能是随机杂乱的，也有可能是 HNSW 索引等结构直接的近似 Top-K 算法得到，但是可能依然不符合需要，而且：**向量相似度 ≠ 语义相关性**，并且初始检索为了速度牺牲了精度。HNSW 等利用的排序思路是余弦相似度，这个虽然速度快但是精度不足够高，且可能忽略很多信息。

- **交叉编码器重新排序：** 将用户查询和每个候选文本块输入到一个 Transformer 模型（如 BERT）中，该模型会评估它们之间的匹配程度。这种方法非常准确，但速度慢且资源密集。当质量比延迟更重要时，此方法最适用。

- **基于分数重新排序：** 使用启发式方法或相关性分数（如 BM25 提升、关键词搜索匹配）调整排序。这种方法速度快、开销小，但精细度较低。

### 3.3 利用元数据优化（Indexing阶段可加入，在Retrieval阶段发挥作用）

利用元数据是指使用结构化标签，如日期、作者、领域或文档类型，来过滤和提升相关结果。元数据过滤是一种投入低、效果显著的技术，因为它不需要大量的计算。

- **日期过滤：** 移除过时数据，只关注最新文档。这在金融等快速变化的领域非常有用。然而，过度关注最新内容有时可能会排除重要的历史文档。

- **作者/来源过滤：** 提升来自可信个人或来源的检索文档。这种方法产生幻觉（hallucination）的可能性很低，但你也可能因此错过一些不那么知名但高度相关的数据。

- **文档类型过滤：** 根据格式（例如，指南、博客或政策文件）进行过滤。虽然这有助于匹配用户意图，但如果元数据不一致，也存在过度过滤的风险。

- **元数据附加**可以为块添加元数据，如页码、文件名等，帮助缩小检索范围，提高精度。在分块后增加元数据。

### 3.4 混合搜索（Retrieval阶段进行）

混合搜索（Hybrid search）结合了基于关键词（稀疏）和基于向量（密集）的检索方法，以提高结果质量。这能显著提高相关性，尤其是在边缘情况或用户查询模糊时。

#### 3.4.1 两类搜索

- **稀疏的匹配**：维度等于整个词表的大小。每个维度对应一个具体的词。对于一篇文档，只有出现在文档中的词的维度有非零值，其他维度全部为 **0**，因此向量是**稀疏** 的。查询也被表示为同样的稀疏向量，通过计算**词重叠程度**来匹配文档。
  
  - **优点**：精确匹配专有名词、ID、特定短语；可解释性强；对低频词敏感。
  
  - **缺点**：忽略语义和同义词（如“汽车”和“轿车”无法匹配）；容易受拼写/分词噪声影响

- **稠密的匹配**：使用深度神经网络（如 BERT、SBERT）将文本映射成一个固定长度的**连续、低维**向量（通常 128~768 维）。每个维度都是浮点数，几乎所有的维度都有非零值，且数值密集分布。查询和文档都被编码为密集向量，通过计算**余弦相似度**或**点积**来度量语义相关性。
  
  - **优点**：能够理解同义词、上下义、意译等深层语义；对词语变体（单复数、时态）鲁棒。
  
  - **缺点**：训练依赖大量数据；计算成本稍高；对稀有词或专有词可能不如关键词匹配精准。

#### 3.4.2 具体操作

- **分数融合：** 使用加权分数结合稀疏和密集方法的搜索结果。这种方法能实现平衡的准确性，但需要仔细调整以避免结果嘈杂。

- **结果合并：** 从两种方法中检索出最佳结果，然后合并并重新排序。这种方法实现简单，但存在重复或排序逻辑不一致的风险。

### 3.5 Small-to-big 分层索引（Indexing阶段作用，Retrieval阶段发挥作用）

- 将原始文档切分为若干 **大块**（例如按段落、章节或固定长度 512 token），每个大块再进一步拆分为若干 **小块**（如按句子、语义片段或固定长度 128 token）。建立映射关系：每个小块都知道自己属于哪个大块（父节点）。

> 常见切分方式：
> 
> - **基于滑动窗口**：小块大小为 128 token，大块大小为 512 token，相邻小块共享重叠区域。
> 
> - **基于语义结构**：以段落或小节作为大块，以句子或短语作为小块。

- 构建向量索引
  
  - **仅对小块的文本进行向量化**，存入向量数据库（如 Milvus, FAISS, Qdrant）。每个向量条目附带元信息：所属大块的 ID 或原文位置指针。
  
  - 大块本身 **不参与向量检索**，仅作为最终返回的“上下文容器”。

- 检索流程：用户输入查询 q
  
  - **小块检索**：对 q 计算向量，在索引中检索与 q 最相似的 top-k 个小块（k 通常较小，如 10~20）。
  
  - **去重与聚合**：根据小块携带的大块 ID，将检索到的小块归并到各自所属的大块中。可以选择只保留匹配命中数最多的大块，或按小块相似度加权汇总。
  
  -  **返回大块**：将筛选出的若干个大块（通常 1~5 个）完整内容作为上下文，拼接后送入生成模型。

- 可选的优化策略
  
  - **混合检索**：小块检索阶段可结合关键词（BM25）和向量检索，进一步提高召回率。
  
  - **重排序（Rerank）**：获取大块后，使用轻量级跨编码器（如 Cohere rerank）对大块进行二次排序，优先取与查询最相关的大块。
  
  - **动态阈值**：只返回那些至少有一个小块匹配度超过阈值的大块，避免引入低相关性的长文本。
  
  - **多级 Small-to-Big**：可扩展为三层（句子→段落→文档），适用于长文档或多文档场景。

### 3.6 查询重写和优化策略（Pre-Retrieval阶段）

- 用户的Query若质量不高，则可能影响最后结果。主要的优化策略包括三大类：**重写、增强、分解**

#### 3.6.1 Query重写-上下文信息补全

- 多轮对话中，用户输入往往隐含上下文信息

- 可以利用LLM对于Query进行重写，把上下文隐藏信息纳入新生成的Query

- 除了使用 LLM 进行查询重写，还有专门的小型语言模型，比如 RRR (Rewrite-retrieve-read)。

#### 3.6.2 Query重写-RAG Fusion（扩展查询）

- 根据原始的Query**生成多个方面的Query**，然后利用RRF（Reciprocal Rank Fusion）技术，把多个结果融合，生成统一排名，增加最相关文档出现的机会

#### 3.6.4 Query增强-HyDE

- 传统的RAG严重依赖查询和文档分块的直接相似度，若措辞不同则可能准确率严重下降

- **Hypothetical Document Embeddings**（HyDE）不是"搜索文档"，而是让系统在检索开始之前，先想清楚理想答案应该长什么样。

```
User Query
      ↓
LLM generates hypothetical answer/document
      ↓
Create embedding of that hypothetical document
      ↓
Search vector database using this richer embedding
      ↓
Retrieve better context
```

核心想法非常简单：生成出来的假设文档，比原始的短查询承载了更丰富的语义。检索系统据此搜索的是"上下文意图"，而不只是关键词层面的相似度。

完整流程如下:

- 1、用户提交查询例如：

```text
"What is LangSmith and why do we need it?"
```

- 2、LLM 生成一份假设文档

LLM 写出一段可能回答这个问题的合成文本。例如：

```text
"LangSmith helps developers monitor, debug, and evaluate LLM applications..."
```

这份文档并不要求事实完全正确，它要表达的是"一个有用答案大致长什么样"。

- 3、生成 Embedding

把假设文档转成向量。这个向量通常比直接对原始查询做 Embedding 信息密度高得多。

- 4、执行向量检索

用这个 Embedding 去向量数据库里做相似度搜索：

```text
Hypothetical Embedding → Similarity Search → Relevant Documents
```

检索关注的是概念上的相关性，而不是浅层的关键词匹配。

- 5、生成最终答案

检索到的文档进入 RAG 的生成阶段，从而拿到更准确、更贴合上下文的回答。

这个设计的妙处在于不需要重新训练检索模型。改变查询的表达方式，就能改善检索质量。

#### 3.6.5 Query增强-Step-back prompting

回溯提示（Step-Back Prompting）是一种高效的提示技术，它旨在辅助大语言模型（LLM）从具体细节中提炼出抽象的概念和基本原则。该技术的核心在于将用户的具体问题转化为一个更高层次的抽象问题，从而帮助模型更有效地进行信息检索和推理。

在现实应用中，用户提出的问题往往包含大量细节，这可能导致大语言模型在直接检索和推理时难以捕捉到问题的本质。例如，在解决物理问题时，如果直接询问“温度增加两倍时，理想气体的体积增加八倍，压力 P 会如何变化？”，模型可能会忽略理想气体定律的基本原则，从而无法准确回答。然而，通过回溯提示，我们首先根据原始问题生成一个更广泛的问题，例如寻找问题背后的基本物理公式。然后，我们从更广泛的问题中获得答案，最后将更广泛问题的答案和原始问题一起提交给 LLM，从而获得正确答案。

同样，对于特定历史人物的教育背景问题，如“Estella Leopold 在1954年8月至1954年11月期间就读于哪所学校？”，由于涉及特定的时间范围，模型直接回答的难度也会增加。

为了解决这些问题，回溯提示建议提出一个更广泛的问题，如“Estella Leopold 的教育经历是什么？”这样的问题不仅涵盖了原始问题，而且可以提供足够的背景信息，从而帮助模型推断出原始问题的答案。这种更广泛的问题通常比原始问题更容易回答，因为它们更容易与模型已有的知识库相匹配。

回溯提示主要包括以下两个步骤：

1. **抽象化（Abstraction）:** 我们首先引导大语言模型提出一个更广泛的问题，关注于高级概念或原则，而非直接解答用户的查询。随后，我们检索与这些概念或原则相关的信息。
2. **推理（Reasoning）:** 基于检索到的关于高级概念或原则的信息，大语言模型可以进行抽象推理，从而推导出原始问题的答案。

通过这种抽象化和推理的过程，回溯提示不仅提高了大语言模型在处理复杂问题时的准确性，而且增强了其在抽象思维和逻辑推理方面的能力。

#### 3.6.6 Query分解-IRCoT

IRCoT的想法是使用检索来指导思维链 （CoT） 推理步骤，并使用 CoT 推理来指导检索。下图显示了IRCoT检索方法的概述。

![](https://pic4.zhimg.com/v2-dd0c8eb880dae07ba7cbb69ce26e4d6b_1440w.jpg)

- 首先使用问题作为查询来检索一组基本段落。

- 随后，我们在以下两个步骤之间交替进行：
  
  - 扩展 CoT：使用问题、到目前为止收集的段落以及迄今为止生成的 CoT 句子来生成下一个 CoT 句子;
  
  - 扩展检索到的信息：使用最后一个 CoT 句子作为查询来检索其他段落以添加到收集的集合中。

- 重复这些步骤，直到 CoT 报告答案或达到允许的最大推理步骤数。终止后，所有收集的段落将作为检索结果返回。

#### 3.6.7 Query分解-least-to-most

Least-to-Most教LLM如何通过将复杂问题，分解为一系列更简单的子问题，来解决复杂问题。它由两个连续阶段组成：

- 复杂问题分解。在这个阶段，Prompt中包含了展示分解过程的示例，其后是待分解的具体问题。

- 子问题解决。此阶段的提示包含三个部分：
  
  - (1) 展示如何解决子问题的恒定示例
  
  - (2) 之前回答的子问题和生成的解决方案的潜在空列表
  
  - (3) 下一个需要回答的问题

### 3.7 检索器微调（Retrieval过程）

- 当上下文与预训练语料不符时，特别是在医疗或法律等术语繁多的专业领域，对于检索器微调可以显著提升检索效果和领域对齐，尽管需要额外的工作量。

- 通过标注的领域数据微调检索模型，通常采用对比学习方法，缩短正样本之间的距离，增加负样本之间的距离。这个过程通过设计损失函数实现。

- 微调大型检索器时，成本较高，尤其是处理像**gte-Qwen**这样基于LLM的检索器时。此时，通过添加适配器模块并进行微调，可以有效降低成本。此外，适配器还能更好地适应特定的下游任务。在预训练模型的内部层之间，插入一些**参数量极小**的神经网络模块（即适配器），然后**冻结原始模型的所有参数**，只训练这些新插入的适配器。原始检索模型拥有通用的语言理解和匹配能力，而适配器在它的每一层内部，学习了一个**低秩的、任务特定的偏移量**。这个偏移量会抑制通用特征、增强领域特征。

### 3.8 蒸馏

对于复杂的 RAG 系统而言，每次都解析大量文档并非最佳选择。上下文蒸馏（Context distillation）有助于将大型文档浓缩成高价值、有意义的摘要。

有两种方法可以实现这一点：

- **基于摘要的蒸馏：** 使用提取式或抽象式摘要来保留关键点。这种方法产生简洁的上下文，但可能会遗漏细节。
- **问题驱动的蒸馏：** 根据具体问题定制上下文。这种方法高度相关，但依赖于准确的查询理解。

### 3.9 后检索压缩（post-retrieval阶段）

- 在RAG系统中，常见的误区是认为检索越多的文档并拼接成更长的提示词有助于提升效果。

- 然而，过多的上下文往往会带来噪声，影响LLM识别关键信息。解决这一问题的常见方法是对检索内容进行压缩和选择。

- 与压缩文档内容不同，选择是直接删除不相关的文档块。通过删除输入中的冗余内容，优化上下文，从而提高语言模型的推理效率。选择性上下文基于基础语言模型计算的自信息来评估词汇的重要性。通过保留自信息较高的内容，该方法能够在不影响性能的前提下，提供更简洁高效的文本表示。

- 另一种常用的方法是让LLM在生成最终答案之前评估检索到的内容，以过滤掉不相关的文档。

## 4 RAG工作流程范式

RAG的流程可以定义为

$$
F = (M_{\Phi_{1}},...,M_{\Phi_{n}})
$$

其中 $\Phi$ 代表模块参数。

模块化RAG流程可以分解为一系列子功能。通过控制逻辑，操作符既可以按预定管道执行，也可以在需要时进行条件判断、分支或循环。在最简单的情况下，这个流程图呈现为线性结构。

通过深入分析当前的RAG方法，我们识别出了一组常见的RAG流程模式，记作  $P$。这些模式跨越了多种应用场景，具有较高的一致性和可复用性，展示了流程设计中的常见结构和行为。一个RAG流程模式可以定义为：

$$
P = \{M_{\Phi_{1}}:\{ Op_1\} → M_{\Phi_{2}}:\{ Op_2\} → ... → M_{\Phi_{n}}:\{ Op_n\} \}
$$

$Op$ 代表操作符

### 4.1 线性模式（Linear Pattern）

<img title="" src="https://pic2.zhimg.com/v2-375a55c6c6432ea9f2c2988cdb6790b7_1440w.jpg" alt="" width="667">

$$
P_{linear} = \{ M_{indexing} → M_{pre-retrieval} → M_{retrieval} → M_{post -retrieval} → M_{generate} \}
$$

线性流程是最为基础且常见的流程模式之一。

常见的线性RAG流程会在预检索阶段包含查询转换模块（如重写或HyDE操作符），并在后检索阶段使用重排序。**Rewrite-Retrieve-Read（RRR）** 是一个典型的线性结构。

查询重写模块是基于T5-large微调的可训练小型语言模型，在强化学习中，重写器的优化被形式化为一个马尔可夫决策过程，LLM的最终输出作为奖励。检索器使用稀疏编码模型BM25。

<img src="https://pic4.zhimg.com/v2-2d6646e6f860cceb83aa08c3b8a542b5_1440w.jpg" title="" alt="" width="665">

### 4.2 条件模式（Condition Pattern）

条件结构的RAG流程根据不同条件选择适合的管道，通常，通过路由模块来决定下一步的模块选择。

<img src="https://pica.zhimg.com/v2-37f69bdb7aa7d4678d550b529dd80b06_1440w.jpg" title="" alt="" width="663">

管道的选择取决于查询的类型或内容，针对不同的场景执行相应的流程。例如，在处理严肃问题、政治话题或娱乐话题时，LLM生成内容的容忍度各不相同。这些路由流程在检索源、检索方式、配置、模型和提示词方面有所差异。

$$
P_conditional = { M_i \xrightarrow{f_r} M_j \land M_k } \}
$$

$f_r$ 表示基于路由函数的选择。

### 4.3 分支模式（Branching Pattern）

在许多情况下，RAG流系统可能会有多个并行运行的分支，通常是为了增加生成结果的多样性。

具有分支结构的RAG流与条件方法不同，它涉及多个并行分支，而不是在条件方法中从多个选项中选择一个分支。从结构上看，它可以分为两类：

- 预检索：每个分支分别执行检索和生成，最后将结果进行汇总。

<img src="https://pic2.zhimg.com/v2-adfd7f9b72f707452df40977c320ac0f_1440w.jpg" title="" alt="" width="588">

- 后检索：仅执行一次检索，然后对每个检索到的文档块分别进行生成，最后进行汇总。

<img src="https://picx.zhimg.com/v2-cc8e1d372df7a9b743d15da0799f3f77_1440w.jpg" title="" alt="" width="586">

假设在模块 $B = M_{\text{split}}(\cdot) = \{b_1, b_2, \dots, b_m\}$ 中生成了多个分支 $b_i$。
对于每个分支 $b_i \in B$，可以执行相同或不同的 RAG 处理流程，经过多个处理模块 $\{M_1, M_2, \dots, M_k\}$ 以获得分支输出结果：

$$
p_i = M_i^k(\dots M_i^2(M_i^1(b_i)) \dots)
$$

多个分支的结果通过聚合函数进行聚合以获得中间输出结果：

$$
\hat{O} = M_{\text{merge}}(\{p_i \mid b_i \in B\})
$$

然而，聚合并不一定是 RAG 流的结束，因为它可以继续连接到其他模块：

$$
M_j^n(\dots M_j^2(M_j^1(\hat{O})) \dots)
$$

例如，在聚合多个模型响应之后，它们可以继续通过验证模块。因此，整个分支流程模式可以表示为：

$$
P_{\text{branch}} = M_{jn}(\dots M_{j1}(M_{\text{merge}}(\{M_{ik}(\dots M_{i1}(b_i) \dots) \mid b_i \in M_{\text{split}}(q)\})) \dots)
$$

### 4.4 循环模式（Loop Pattern）

循环结构是模块化RAG的核心特征，涉及检索与生成步骤的相互依赖。

<img src="https://pica.zhimg.com/v2-725868edc1d0d80a4586319d9cb67186_1440w.jpg" title="" alt="" width="673">

循环模式可以分为**迭代、递归**和**自适应（主动）检索方式**。

#### 4.4.1 迭代模式

对于复杂问题，单次检索与生成可能无法提供足够的知识支持，因此可以采用迭代方法。

在每个迭代步骤 $t$ 中，根据查询 $q_t$ 和之前的输出序列 $y_{<t}$ 进行迭代，迭代条件为 $t$ 小于最大迭代次数 $T$。
每次循环中，使用前次输出 $y_{t-1}$ 和当前查询 $q_t$ 检索文档块 $D_{t-1}$，随后生成新的输出 $y_t$。
是否继续迭代由 Judge 模块决定，其判断依据包括 $y_t$、$y_{<t}$、$q_t$ 和 $D_{t-1}$。

一个典型的迭代检索案例是**ITER-RETGEN**，它迭代执行检索增强生成和生成增强检索。每次迭代中，ITER-RETGEN利用前一轮的生成结果作为上下文，帮助检索更相关的知识，循环在达到预设迭代次数后终止。

<img src="https://pic2.zhimg.com/v2-6338ea690badc1c4e434c66a43fe0e03_1440w.jpg" title="" alt="" width="690">

#### 4.4.2 递归模式

递归检索的特点在于其对前一检索步骤的依赖，并逐步加深检索，通常以树状结构进行，且有明确的退出机制。递归检索通常伴随查询转换，即每次检索基于重新改写的查询进行。

一个典型的递归检索例子是**澄清树（Tree of clarifications，ToC）**，它通过递归扩展澄清树，将初始的模糊问题转化为一系列明确的问题。当达到最大节点数或最大深度时，树的构建终止。最终，ToC整合所有有效节点，生成完整的长文本答案。

<img src="https://picx.zhimg.com/v2-e3591624396e67edc0b632ea22624aaf_1440w.jpg" title="" alt="" width="708">

#### 4.4.3 自适应模式

随着RAG的发展，检索方式逐渐从被动转向自适应，也称为**主动检索**，这部分得益于LLM的强大能力。RAG系统能够主动决定何时进行检索，并选择何时结束流程并生成最终结果。根据不同的判断标准，自适应检索可以分为基于提示词工程（Prompt）和基于微调的方式。

#### 4.4.4 基于提示词的检索

通过提示词工程来控制LLM的行为，典型例子是**FLARE**。其核心思想是，只有在知识缺乏时才进行检索，以避免不必要的检索。FLARE会生成临时句子，并检测是否存在低概率token。如果发现低概率token，系统会检索相关文档并重新生成句子。生成的临时答案会进行置信度评估，如果未达到所需的置信度水平，流程会返回到检索阶段并重新生成。评估标准通过提示词实现。

<img src="https://pica.zhimg.com/v2-44cb4aa967a7df2c783f3022a174904e_1440w.jpg" title="" alt="" width="660">

#### 4.4.5 基于微调的检索

基于微调的检索。通过微调LLM生成特殊的token，触发检索或生成步骤。该概念源自Toolformer，在RAG系统中用于控制检索和生成。一个典型例子是Self-RAG，首先预测生成特定的“检索”token是否有助于增强生成过程，如果需要检索，模型生成批判token来评估检索段落的相关性，并最终选择最优结果作为最终输出。它提示GPT-4生成一个适合的指令微调数据集，以微调所部署的开源LLM。这样可以让模型在生成过程中输出四个特定的控制RAG流程的标记。
<img src="https://pic4.zhimg.com/v2-23adead696df1dffb0fbc6fd327130f5_1440w.jpg" title="" alt="" width="663">

### 4.5 调优模式（Tuning Pattern）

在模块化RAG中，许多组件由可训练的语言模型组成。通过微调，可以进一步优化组件性能，并增强其与整体流程的协调性。本节将介绍三种主要的微调模式，即检索器微调、生成器微调和双重微调。

#### 4.5.1 检索器微调

在RAG流程中，常见的检索器微调方法，包括：

- **直接对检索器进行监督微调**。构建专门用于检索的数据集，并对密集型检索器进行微调。例如，可以使用开源的检索数据集，或者根据特定领域的数据构建数据集。
- **添加可训练的适配器模块**。有时，直接对API向量模型（如**OpenAI Ada-002**或**Cohere**）进行微调并不可行。此时可以引入适配器模块来增强数据表示，并且适配器模块有助于更好地与下游任务对齐，无论是特定任务（如**PRCA**）还是通用任务（如**AAR**）。
- **语言模型监督检索（LSR）**。通过LLM生成的结果对检索器进行微调，提升其性能。
- **基于LLM输出的强化学习**。依然使用LLM的输出结果作为监督信号，利用强化学习来使检索器与生成器保持一致。整个检索过程被分解为生成式马尔可夫链。

<img src="https://pic2.zhimg.com/v2-22ac0bfe783fcf80980899ee147d2adb_1440w.jpg" title="" alt="" width="614">

#### 4.5.2 生成器微调

在RAG流程中，生成器微调的主要方法：

- **直接监督微调**。通过外部数据集微调生成器，可以为其补充额外的知识。另外，通过定制输入和输出格式，生成器可以适应特定的数据格式，按照指令生成输出。
- **蒸馏**。对于本地部署的开源模型，一种有效的优化方法是使用GPT-4批量构建微调数据，从而增强开源模型的能力。
- **基于LLM/人类反馈的强化学习**。基于最终生成答案的反馈进行强化学习。除了人工评估，强大的LLM也可以作为评估工具，帮助改进模型的表现。

<img src="https://pic3.zhimg.com/v2-3e1db501d6641566f2007e88a90b644a_1440w.jpg" title="" alt="" width="627">

### 4.5.3 双重微调

在RAG系统中，同时对检索器和生成器进行微调是其独有的特性。系统微调的关键在于检索器与生成器的配合。一个典型的实现是**RA-DIT**，该系统同时微调LLM和检索器。LLM的微调部分旨在通过检索增强的指令提高生成正确答案的可能性；而检索器的微调部分则通过最小化检索评分分布与LLM偏好之间的KL散度来优化检索器。在这种模式中，检索器和生成器都会参与微调，并使它们的偏好对齐。
