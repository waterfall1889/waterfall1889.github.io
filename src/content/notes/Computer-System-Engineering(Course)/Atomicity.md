# Atomicity and Crash Recovery

## 1 What is Atomicity

- 金融行业的管理系统系统崩溃时会出现一致性问题，这在金融系统不可接受。

- 例如银行转账，要保证一方的钱被扣的同时另一方的钱增加。我们要保证任何一行代码崩溃的情况下系统的一致性仍不会出错。

- 因此我们希望，很多涉及多个数据读写的操作，要么全部做完，要么完全不做，这就是原子性。（all-or-nothing）

## 2 Shadow Copy and Copy-on-Write

**Shadow Copy（影子拷贝）** 是一种常见的数据备份与版本管理技术，用于在不干扰当前系统运行的情况下，对数据或文件创建一致性的快照（snapshot）。在写入或修改数据之前，先把原始数据的“影子副本”保留下来。

**写时复制（CoW）** 是一种资源管理优化策略：当多个任务需要读取同一份资源（内存页、文件数据）时，它们共享同一份物理副本；**只有当某个任务试图修改该资源时，系统才会为它创建一份独立的私有副本，修改操作在此副本上进行，对其他共享者不可见。** 即"读时共享，写时分离"。

但是shadow copy也无法避免所有问题，比如，非原子性实现的rename过程中的崩溃：

```
F:文件inode
A:原始目录项
B:修改后目录项

初始：A→F
状态I：A→F  B→F refcnt=1
状态II：B→F refcnt=1
```

但是如果在状态I和II之间发生了崩溃，那么会留下中间状态，恢复时无法弄明白到底哪一个目录项才是修改后需要保留的。**Shadow Copy 保住了旧状态，却没有记录“这两个版本里哪个才是应该提交的新状态”。**

### 2.1 Shadow copy的缺陷

- 空间开销大
  
  - 每次写入都可能触发“复制旧版本”操作（copy-on-write）。
  
  - 如果修改量很大或快照频繁，系统会保留大量历史版本，占用 额外存储空间。
  
  - 特别是在大文件系统中，一个快照可能导致磁盘空间迅速被吃完。

- 写入性能下降（Write Amplification）
  
  - 写入时不再是“直接覆盖”，而是：先复制原数据到影子区；再修改原位置。
  
  - 这会导致两次写操作（一次复制 + 一次更新）。
  
  - 对 I/O 密集型应用（如数据库、日志写入）影响明显。

- 管理复杂
  
  - 需要维护多个版本之间的依赖关系（哪个块属于哪个版本）。
  
  - 删除旧快照时必须安全清理引用，否则可能破坏当前版本。
  
  - 若实现不当，容易导致“引用悬挂”或“数据孤立”。

- 一致性保障有限
  
  - 如果系统崩溃在“复制影子”和“写入新数据”之间，可能造成部分数据未被复制、快照状态不一致、难以恢复（除非配合 journaling 或事务日志）。

- 难以处理跨文件或跨卷操作
  
  - Shadow copy 通常在单卷（volume）或单文件系统内工作。
  
  - 若操作涉及多个卷（如跨分区 rename），影子拷贝无法保证全局一致性。

- 快照链过长导致性能劣化
  
  - 多次创建快照会形成“快照链”，读取最新数据时必须追溯多个层级。
  
  - 这种“层层查找”的开销会显著降低读性能。

- 很难实现多人协作文件系统

## 3 语义恢复

**应用程序的恢复方法应当与文件系统的恢复方法相互独立。** 在分布式系统或文件系统中，数据可能会因为崩溃、断电、硬件故障等原因丢失或损坏。

为了保证系统一致性，通常会有两类恢复机制：

- **文件系统恢复**：文件系统检测异常后，恢复数据结构和文件元数据的一致性（Journaling、shadow copy、日志重放）

- **应用程序恢复**：应用自身对数据进行恢复或保证操作的原子性（数据库事务回滚、KVStore 重试机制）

**为什么应用程序和文件系统需要解耦？**

解耦的好处在于：应用程序只管“业务数据的一致性”，文件系统只管“存储的一致性”，互不干扰，既增强容错能力，又提高系统可维护性和可移植性。同时具有更强的容错能力，即使文件系统恢复失败，应用程序仍可通过自身机制进行数据恢复。避免“单点依赖”导致的数据丢失。还可以简化复杂度，应用关注业务逻辑的恢复（如数据库回滚），文件系统关注存储一致性（如磁盘元数据），避免两者的逻辑交叉、增加出错概率。

## 4 Journaling

Journaling机制，是一个常见的文件系统技术，用于保证文件系统的一致性，特别是系统崩溃或者断电的时候。**在对文件系统执行修改操作前，先把“操作意图”写入一个日志（journal）。系统根据日志记录执行实际修改。一旦修改完成，标记日志已完成或删除。系统崩溃后，可以根据日志重放（redo）或回滚（undo），确保文件系统一致。日志可以选择在某个专门划出的最后的block进行记录。**

Journaling实际上也有缺陷，**日志占用大量空间，会造成在下载大文件时空间不足。**（日志区大小固定。在下载超大文件时，若采用 data=journal 模式，数据会塞满日志区。文件系统被迫频繁触发 Checkpoint 以清空日志，导致下载速度出现剧烈波动，甚至报错“设备空间不足”（实际主数据区空间充足，但日志区无空闲事务槽位）。）

 journaling 通常只保证 metadata 的一致性，而不是文件数据内容（user data） 的一致性。因此不能用journaling实现原子的fsync。

**缓解方案**：

- 仅对于元数据做journaling日志保护

- 数据采用单次写入方式

- 数据保护方案：提供三种保护级别
  
  | 模式 (Mode)          | 记录内容               | 工作方式                                                   | 优点                                                              | 缺点                                                  |
  | ------------------ | ------------------ | ------------------------------------------------------ | --------------------------------------------------------------- | --------------------------------------------------- |
  | **data=journal**   | **元数据 + 用户数据**     | 数据和元数据都先写入日志，再异步刷入主数据区。                                | **最强一致性**。断电后数据不丢失，且无陈旧数据风险。                                    | **性能最差**。数据写入两次（日志一次，主区一次），占用大量日志空间，极易导致日志满而阻塞 I/O。 |
  | **data=ordered**   | **仅元数据**（但保证数据先落盘） | **这是大多数 Linux 发行版的默认模式**。先写入用户数据到主数据区，**再**将元数据变更写入日志。 | **性能与安全的良好平衡**。保证在元数据日志提交前，相关用户数据已存在磁盘上。即使崩溃，文件大小正确，读取不会得到垃圾数据。 | 不保证用户数据的即时持久化（若数据写入后、元数据提交前断电，数据可能丢失，但文件系统结构不受损）。   |
  | **data=writeback** | **仅元数据**           | 数据与元数据完全独立写入，不保证顺序。元数据日志可能先于数据落盘。                      | **性能最高**（接近无日志的异步模式）。                                           | **最不安全**。崩溃时，文件可能指向尚未写入的磁盘块，读取到完全随机的旧数据（数据损坏风险）。    |

- 使用 fsync 系统调用：同步刷新数据到磁盘，等待数据完全写入后再继续后续操作

## 5 Logging For Atomicity

这是更加通用的做法，思想和journaling有类似之处。核心思想是记录日志信息，使得我们可以完成崩溃后的恢复。

**Logging和journaling的核心区别在于前者有transaction的概念。**

我们可以这样认为，**Transaction本质是一种标记，标记哪些事情需要原子化**

| 阶段    | 英文名称                                    | 状态              | 是否可以 Abort / Rollback | 核心含义                                                                                                             |
| ----- | --------------------------------------- | --------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **①** | **First step of all-or-nothing action** | 事务开始            | 可以                    | 事务从这里开始执行，例如修改数据库记录、更新文件系统 metadata、写入日志。这是“一系列原子操作”的起点。                                                         |
| **②** | **Pre-commit discipline**               | **未提交**         | 可以                    | 事务尚未真正提交，修改仍属于暂存状态，可以随时中止并回滚，不应对外产生不可逆的影响。                                                                       |
| **③** | **Commit-point**                        | **已提交（Commit）** | 不可回退                  | **关键分界点。** 一旦越过 commit point，事务被认为已经成功提交，从 `nothing` 进入 `all`。系统必须保证提交结果最终能够持久化；通常要求相关 WAL / journal 已经安全写入稳定存储。 |
| **④** | **Post-commit discipline**              | **已提交但未完全完成**   | 不可回退                  | 主存储中的最终修改可能尚未全部完成，但已经有持久化日志保证其最终完成。若此时崩溃，恢复过程通过 **redo** 等机制继续完成事务。                                              |
| **⑤** | **Last step of all-or-nothing action**  | **完全完成**        | 不可回退                  | 事务执行结束，所有修改已经完成并持久化到主数据存储中。事务从“已提交但尚未完全应用”进入最终完成状态。                                                              |

Logging很大的不同在于，没写完的logging可以舍弃，而写完的logging则可以在崩溃时恢复数据，因此logging可以很好实现“all-or-nothing”。对于数据库而言logging是最常用的atomicity方法。

**Logging 通常以 transaction 为核心抽象，将一组相关修改作为一个逻辑整体记录，并通过 commit/abort 等机制实现原子性和恢复。Journaling 则主要将日志机制应用于文件系统 crash consistency，通过记录文件系统状态修改及其提交状态，使系统崩溃后能够恢复到一致状态。**
