# Remote Procedure Call

## 1 分布式系统基本设计

<img src="images/2026-08-25-09-03-14-image.png" alt="" width="565">

- 用户通过互联网访问，CDN（内容分发网络）用于缓存静态资源（如图片、CSS、JS），起到就近加速访问、大幅减少源站带宽压力的作用。

- 负载均衡器负责将海量用户请求按策略（如轮询、最小连接数）分发到后端的应用服务器集群，同时负责健康检查，屏蔽故障节点。

- 服务器是无状态的服务节点，负责执行具体的业务代码（如订单生成、价格计算）。无状态性使其支持横向弹性伸缩。

- 数据层面，设计分布式文件系统、分布式数据库、消息队列、分布式缓存

## 2 局域网共享文件存储的解决方案

- 分布式系统一个重要的问题是解决不同机器在局域网内的文件共享存储。

- 解决思路有很多，比如Web Socket是一个好的思路，但是Web Socket比较复杂，实现和程序编写比较麻烦

- 一个更直接的机制是，利用下面提到的RPC——Remote Procedure Call

## 3 RPC

RPC的核心效果是，**让用户像调用本地函数或者接口一样去调用远程机器上的函数或者接口**；目的是为了屏蔽类似于Web Socket使用中网络通信的复杂过程。

通信代理层是Stub，负责隐藏网络底层的通信细节，让上层代码能够像调用本地函数一样调用远程服务。

<img src="images/2026-08-25-10-37-05-image.png" alt="" width="484">

Stub分为两个部分，客户端Client Stub和服务端Stub。

客户端的Stub主要负责：

- 打包参数，把参数序列化为网络格式

- 请求发送，通过网络将请求发送到服务端

- 同步等待，阻塞服务等待服务端的响应

- 结果解析，把响应数据反序列化为本地的对象

服务端的Stub主要负责：

- 请求监听，持续性监听来自客户端的请求

- 参数提取，从请求解析函数参数

- 服务调用，调用实际的业务逻辑

- 结果打包并且序列化

- 把结果发送回给客户端

## 4 Message设计

### 4.1 服务标识（Service ID）

唯一标识要调用的远程服务或函数，有多种方式。

可以采用函数名称/方法ID/服务的路径实现。

### 4.2 服务参数

作用：传递给远程函数的实际参数数据，参数不能包含指针
内容：

- 函数调用所需的输入参数

- 参数类型信息

- 参数值数据

### 4.3 序列化/反序列化

- Marshal（序列化）：将内存中的数据结构转换为可传输的字节流，对于指针需要先进行marshal转化再发送。

- Unmarshal（反序列化）：将接收到的字节流还原为内存中的数据结构，对于指针传送后需要进行恢复。

| 字段层级                 | RPC 请求 (Request)                                                           | RPC 回复 (Reply)                                                                                                                            | 核心作用与差异                                                                                                                                 |
| -------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **1. 事务标识**          | **Xid** (Transaction ID)                                                   | **Xid** (Transaction ID)                                                                                                                  | **请求与回复一一对应**。客户端发送时记住该 ID，收到回复时根据 Xid 进行**分发（Dispatch）**，找到是哪个请求得到了响应。                                                                 |
| **2. 消息类型**          | `call`                                                                     | `reply`                                                                                                                                   | 标记该数据包是发起调用还是返回结果。                                                                                                                      |
| **3. 协议版本**          | **RPC 版本号** (rpc version)                                                  | （通常不在此处重复，包含在协议头）                                                                                                                         | 请求方告知使用的 RPC 协议版本，供服务端校验。                                                                                                               |
| **4. 服务寻址**（服务端据此分发） | **程序号 (program #)**<br>**程序版本 (program version)**<br>**过程号 (procedure #)** | （无此字段）                                                                                                                                    | **请求独有**。服务端根据这三个字段定位到底要调哪个服务的哪个具体函数。                                                                                                   |
| **5. 认证信息**          | **认证信息** (auth stuff)                                                      | **认证信息** (auth stuff)                                                                                                                     | 请求时携带客户端凭证；回复时可能携带服务端的认证挑战或结果。                                                                                                          |
| **6. 参数 / 负载**       | **参数** (arguments)                                                         | （视情况，见下方）                                                                                                                                 | 请求携带输入数据；回复则取决于执行是否成功。                                                                                                                  |
| **7. 执行状态**          | （无）                                                                        | **1. 是否接受 (accepted?)**<br>   - 是 (Yes)<br>   - 否 (No)：如 RPC 版本错误、认证失败<br>**2. 是否成功 (success?)**<br>   - 是 (Yes)<br>   - 否 (No)：如程序/过程号错误 | **回复独有**。采用**双层状态码**：<br>1. **协议层（accepted）**：网络连接和协议是否认可这次请求。<br>2. **应用层（success）**：即使请求被接受，业务逻辑是否执行成功（类似 HTTP 的 200 OK 但业务返回 false）。 |
| **8. 返回数据**          | （无）                                                                        | **结果 (results)**                                                                                                                          | 只有 `accepted` 且 `success` 均为是时，此处才包含有效的业务返回数据。                                                                                          |

## 5 Binding过程

<img src="images/2026-08-25-11-04-29-image.png" alt="" width="597">

- RPC的实现框架中，gRPC是最重要的之一，下面是gRPC的binding过程

- **服务器端：** gRPC 底层会创建 TCP Socket，调用 bind() 将其与端口 50051 关联，并调用 listen() 进入监听状态。
  
  - 0.0.0.0是一个通配地址 (Wildcard Address)。它表示服务器会监听本机所有可用的网络接口（网卡）。
  
  - 这意味着，无论是客户端通过 127.0.0.1（回环）、192.168.x.x（内网）、还是公网 IP 发来的连接请求，只要目标端口是 50051，这个服务器都能接收。
  
  - 监听端口号 50051（大于 1024），所以不需要 root 权限即可启动。

- **客户端**：CreateChannel 并不会立即建立网络连接（gRPC 默认是 Lazy Connect，在首次发送 RPC 请求时才拨号）。
  
  - 但当它拨号时，底层执行的是 connect() 系统调用。
  
  - 客户端会通过操作系统的 DNS 解析器（或 /etc/hosts 文件）将 localhost 解析为 IPv6 的 ::1 或 IPv4 的 127.0.0.1。

| 步骤             | 服务器 (0.0.0.0:50051)                                                                         | 客户端 (localhost:50051)                                                                  |
| -------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **1. 解析地址**    | 解析 `0.0.0.0` -> 内核的 `INADDR_ANY`                                                            | 解析 `localhost` -> `127.0.0.1` (或 `::1`)                                                |
| **2. 创建套接字**   | `socket(AF_INET, SOCK_STREAM, 0)`                                                           | `socket(AF_INET, SOCK_STREAM, 0)`                                                      |
| **3. 设置选项**    | (可选) `setsockopt(SO_REUSEADDR)` 以便快速重启                                                      | 无                                                                                      |
| **4. 核心动作**    | **`bind(ip=0.0.0.0, port=50051)`**<br>--> 系统内核在端口表中标记该端口被占用。<br>--> 调用 `listen()` 进入被动打开状态。 | **`connect(ip=127.0.0.1, port=50051)`**<br>--> 内核自动分配源端口（如 52341）。<br>--> 发起 TCP 三次握手。 |
| **5. gRPC 握手** | 接受连接，升级至 HTTP/2，发送 SETTINGS 帧。                                                              | 接收 SETTINGS 帧，确认 HTTP/2 连接建立。                                                          |

## 6 参数传递

- 常见的参数传递有两种思路，值传递和引用传递，在RPC中只能选择前者，因为后者涉及到指针，会带来错误。

- RPC要求必须转化成没有指针的数据参与传输。服务器端再重新建立成有指针的数据结构。

- 参数传递实际上很复杂，编码顺序（大端法、小端法）、浮点数表示、对齐方法、变量的占用空间大小都会带来很多问题。还需要考虑升级的兼容性问题。

- 因此需要考虑规范的统一编码方式。例如Json、XML、Google Protocol Buffers 等**跨语言格式**。这种编码还利于人的阅读，便于debug。不过也存在缺陷：存在模糊和二义性，二进制的strings需要重新的编码，且需要使用更多的空间（tags like <xx> </xx> in XML）

- 还有可以利用**语言内置序列化工具**，常见语言特定格式：
  
  - Java: java.io.Serializable
  
  - Python: pickle 模块
  
  - C#: BinaryFormatter
  
  - Ruby: Marshal

但是存在一些问题，语言绑定问题 (Language Lock-in)使得跨语言互操作性差，版本兼容也比较困难，旧版本数据无法兼容新版本代码。

另一种思路是利用**二进制格式**，优点是更紧凑、准确，缺点是对人类阅读不友好，不利于调试处理。二进制和跨语言格式目前都很常见。二进制还可以进行进一步压缩使得信息内容更加紧凑。但是过度压缩会带来更多的解码时间，因此实际上需要做权衡。网络快速的情况下可以不追求极高的压缩。

## 7 RPC failure

一般来说本地PC（函数调用）不会出现Failure的问题，但是RPC可能出现。可能原因很多，比如参数格式错误、服务器崩溃、网络故障等等。

一次RPC可能出现不同的执行次数，语义上有三种常见场景：

- 最多一次 (At-Most-Once)
  
  - 系统保证请求不会被执行超过一次
  
  - 可能因为故障而根本不执行
  
  - 实现相对简单

- 至少一次 (At-Least-Once)
  
  - 系统保证请求至少执行一次
  
  - 在失败情况下会重试，可能导致重复执行
  
  - 需要业务逻辑处理幂等性

- 正好一次 (Exactly-Once)
  
  - 系统保证请求正好执行一次
  
  - 最理想但最难实现
  
  - 需要复杂的去重和事务机制

有一个专有名词进行描述：**幂等性（Idempotence）**。这意味着对同一个操作，无论执行一次还是多次，结果都相同（系统状态不会被重复改变）。

非幂等性（Non-idempotent）指的是，对同一个操作，执行一次和多次会带来结果的不同。
